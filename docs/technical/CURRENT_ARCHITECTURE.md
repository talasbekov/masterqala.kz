# Текущая архитектура MasterQala.kz

Статус документа: описание фактической реализации первой версии по состоянию репозитория.

## 1. Общая схема

MasterQala.kz реализован как TypeScript-монорепозиторий на `pnpm`:

- `apps/api` — backend на NestJS;
- `apps/web` — единое React PWA для клиента, мастера и оператора;
- `packages/ui` — общие UI-компоненты;
- PostgreSQL 16 + PostGIS — основная база данных и географические запросы;
- pg-boss — фоновые задания и отложенные таймауты;
- Socket.IO — realtime-события;
- локальное файловое хранилище — документы мастеров и фотографии заявок;
- mock payment provider — имитация платежей, пополнений, выплат и возвратов.

```text
React PWA
  ├─ HTTP/JSON ───────────────► NestJS API
  └─ Socket.IO + JWT ─────────► RealtimeGateway
                                  │
NestJS modules                   ├─ PostgreSQL/PostGIS
  ├─ auth                        ├─ pg-boss
  ├─ masters                     ├─ local uploads
  ├─ orders                      └─ mock payments
  ├─ planned-orders
  ├─ disputes
  ├─ reviews
  ├─ wallet / lead credits
  └─ admin / admin-users /
     admin-masters / admin-orders
```

Диаграмма сокращённая: помимо перечисленных подключены модули addresses, payments,
pricing, routing, queue, realtime, audit-log, commercial-mode, uploads, users и health
(полный список — `apps/api/src/app.module.ts`).

## 2. Backend

### 2.1 Технологии

Фактический backend-стек:

- JWT;
- Socket.IO;
- pg-boss;

### 2.2 Модульность

Основные домены разделены на NestJS-модули. Ключевая бизнес-логика находится в сервисах, а контроллеры выполняют роль HTTP-адаптеров.

### 2.3 Как решаются гонки

Это самая нагруженная часть системы: три мастера могут нажать «Принять» одновременно,
а pg-boss имеет право доставить джобу дважды. Механизмов пять, и каждый закрывает
свой класс гонок.

**Переходы статусов — атомарный гейт.** Каждый переход идёт через `updateMany` с
проверкой текущего статуса в `WHERE`. Если строк обновилось ноль, статус уже изменил
кто-то другой, и сервис отвечает `409`, а не перезаписывает состояние. Метод `gate()`
в `orders/orders.service.ts`.

**Волны защищены монотонным гейтом.** Джоба волны обновляет заявку с условием
`wave: { lt: wave }`. Повторная доставка той же джобы не пройдёт условие и не разошлёт
офферы второй раз.

**Лимит SMS — advisory-lock.** Иначе два параллельных запроса кода прочитали бы один
и тот же счётчик и оба прошли лимит.

**Начисления и ставки — уникальные индексы.** `Accrual.orderId`, `OrderOffer`
`(orderId, masterUserId, attempt)`, `PlannedOrderBid` `(plannedOrderId, masterUserId)`.
Идемпотентность обеспечивается базой, а не аккуратностью кода.

**Списание кредита — условный декремент.** `updateMany` с `balance: { gte: 1 }`:
параллельные отклики не уведут баланс в минус.

### 2.4 Авторизация

- вход выполняется по номеру телефона и SMS-коду;
- SMS-провайдера нет: `ConsoleSmsSender` пишет код в лог во всех окружениях,
  кроме production, где текст маскируется и в лог попадает только факт
  недоставки. Реальный шлюз остаётся блокером перед пилотом — без него в
  production вход невозможен;
- после подтверждения выдаётся JWT;
- HTTP endpoints защищаются `JwtAuthGuard`;
- Socket.IO проверяет JWT во время handshake;
- после подключения пользователь входит в персональную комнату `user:<userId>`.

В Prisma сейчас существуют системные роли `CLIENT` и `OPERATOR`. Мастер не является отдельной ролью пользователя: возможности мастера определяются наличием `MasterProfile` и его статусом.

### 2.5 Данные

Основные сущности:

- `User`;
- `MasterProfile`, категории и документы мастера;
- `Order` и `OrderOffer` для срочного режима;
- `PlannedOrder` и `PlannedOrderBid` для планового режима;
- `PaymentTransaction`;
- `Accrual`;
- `LeadCreditAccount` и журнал операций;
- `MasterWalletAccount` и заявки на вывод;
- `Dispute`;
- `Review`;
- сохранённые адреса;
- присутствие и геопозиция мастера.

Денежные значения хранятся целыми числами в тенге. Географические точки срочных заявок и присутствия мастеров хранятся как `geography(Point, 4326)`.

## 3. Срочный режим

### 3.1 Создание

Клиент получает предварительный расчёт через `POST /orders/preview`, затем создаёт заявку через `POST /orders`.

Backend:

1. проверяет категорию;
2. запрещает вторую активную срочную заявку;
3. ищет потенциальных мастеров и рассчитывает выезд;
4. создаёт заказ и географическую точку;
5. создаёт HOLD на полную стоимость выезда;
6. переводит `CREATED → SEARCHING`;
7. ставит первую волну матчинга в pg-boss.

### 3.2 Матчинг

Используются три последовательные волны:

| Волна | Радиус | Ожидание |
|---|---:|---:|
| 1 | 3 км | 60 секунд |
| 2 | 6 км | 60 секунд |
| 3 | 10 км | 90 секунд |

Оффер получают только подходящие активные мастера. Принятие защищено атомарным переходом `SEARCHING → ACCEPTED`. Первый мастер выигрывает; остальные получают `offer:closed`.

### 3.3 Выполнение

Основная цепочка:

`CREATED → SEARCHING → ACCEPTED → MASTER_ON_WAY → INSPECTION → AWAITING_PRICE_CONFIRM → IN_PROGRESS → DONE → CLOSED`.

- на подтверждение цены клиенту даётся 15 минут;
- после отметки мастера «Выполнено» заявка автоматически закрывается через 24 часа, если спор не открыт;
- при отмене мастером на раннем этапе поиск перезапускается с первой волны, а мастеру фиксируется санкция;
- при отсутствии мастеров HOLD аннулируется.

## 4. Плановый режим

Клиент создаёт опубликованную заявку с датой, временным слотом, районом, описанием и необязательным бюджетом.

Ограничения:

- горизонт планирования — 14 дней;
- максимум 5 ставок на заявку;
- один мастер может сделать только одну ставку;
- подтверждение выбранным мастером — в течение 2 часов;
- автозакрытие после выполнения — 24 часа.

В `PAID_MOCK` каждая ставка уменьшает баланс мастера на один lead-кредит и создаёт
операцию `SPEND`; в `FREE_PILOT` ставка создаётся без списания. Режим берётся из
поля `commercialMode` самой заявки, а не из текущего env.

Основная цепочка:

`CREATED → PUBLISHED → MASTER_SELECTED → CONFIRMED → IN_PROGRESS → DONE → CLOSED`.

Также предусмотрены `EXPIRED`, отмены обеими сторонами и `DISPUTE`.

## 5. Realtime

Клиент отправляет:

- `presence:online`;
- `presence:offline`;
- `geo:update`.

Сервер отправляет, в зависимости от сценария:

- `offer:new`;
- `offer:closed`;
- `order:status`;
- `master:location`;
- `bid:new`;
- `bid:selected`;
- `bid:closed`;
- события изменения плановой заявки и операторских действий.

`geo:update` мастера во время поездки пересылается клиенту вместе с расчётным ETA.

## 6. Фоновые задания

pg-boss используется для 18 типов задач (полный список ключей —
`apps/api/src/queue/queue.constants.ts`).

Бизнес-таймауты:

- последовательные волны срочного матчинга (`WAVE`);
- истечение офферов (`WAVE_TIMEOUT`);
- таймаут подтверждения цены (`PRICE_TIMEOUT`);
- автозакрытие срочной заявки (`AUTO_CLOSE`);
- таймаут подтверждения выбранным мастером (`PLANNED_CONFIRM_TIMEOUT`);
- истечение плановой заявки (`PLANNED_EXPIRY`);
- автозакрытие плановой заявки (`PLANNED_AUTO_CLOSE`).

Presence, загрузки и безопасность:

- `PRESENCE_SWEEP` — сброс устаревшего присутствия мастеров (cron раз в минуту);
- `UPLOAD_CLEANUP` — очистка просроченных карантинных загрузок (`PendingUpload`);
- `UPLOAD_SCAN` / `UPLOAD_SCAN_SWEEP` — антивирусный скан карантина загрузок;
- `MASTER_DOCUMENT_SCAN` — скан документов мастера;
- `DISPUTE_EVIDENCE_SCAN` — скан доказательств споров;
- `PERSISTENT_FILE_SCAN_SWEEP` — досканирование постоянных файлов;
- `SECURITY_RETENTION` — retention данных безопасности;
- `SECURITY_ALERT_DELIVERY` / `SECURITY_ALERT_DELIVERY_SWEEP` /
  `SECURITY_ALERT_SLA_SWEEP` — доставка security-алертов и контроль SLA;
- `SECURITY_DEPENDENCY_SWEEP` — ежеминутная проверка зависимостей (Postgres,
  pg-boss, ClamAV): на переходе UP→DOWN пишется событие
  `SECURITY_DEPENDENCY_DOWN`, из которого триггер БД создаёт alert.

В e2e pg-boss можно отключить через `PGBOSS_DISABLED=1`.

## 7. Платежи в текущей реализации

В DI подставлен `CommercialPaymentProvider`: в `PAID_MOCK` он делегирует
`MockPaymentProvider` (успешный результат; `ConflictException` при capture/void
без холда), в `FREE_PILOT` возвращает виртуальные транзакции без записей в БД,
а charge/payout завершаются `FAILED`. В `PAID_MOCK` создаются реальные записи
бизнес-журнала:

- `HOLD`;
- `CAPTURE`;
- `VOID`;
- mock charge для покупки lead-кредитов;
- mock payout для вывода;
- mock refund.

Это означает, что интеграции с банком ещё нет, однако финансовая state machine уже действует. Mock-платежи нельзя считать бесплатным пилотным режимом: это разные вещи, и режим заявки хранится в её поле `commercialMode` (см. [`DATA_MODEL.md`](./DATA_MODEL.md)).

**Ценовой инвариант.** `PricingConfig` роняет приложение на старте, если
`SERVICE_FEE_MIN >= PRICING_BASE_FARE` (`pricing.config.ts`, конструктор) — иначе
компенсация мастеру на минимальном заказе уходит в ноль или минус. Проверка живёт
в `PricingModule`, а не в `validateEnvironment`.

## 8. Хранение файлов

Документы мастера, фото заявок и доказательства споров лежат на локальном диске
(`UPLOAD_DIR`), в БД — только путь и метаданные.

Отдаются они **не статикой, а через контроллеры с проверкой прав**: фото заявки
увидит только её клиент, назначенный мастер или оператор. Публичных бессрочных URL
у этих файлов нет.

Загрузка проходит карантин по модели fail-closed: пока проверка сигнатуры и
антивирус не завершились успешно, файл не отдаётся. Статус доступен отдельными
эндпоинтами, см. [`REST_API.md`](./REST_API.md) и [`FILE_UPLOAD_SECURITY.md`](./FILE_UPLOAD_SECURITY.md).

Локальный диск — первое, что придётся заменить на объектное хранилище при переезде
на несколько инстансов API.

## 10. Локальный запуск

Инфраструктура разработки включает две PostGIS-базы:

- `localhost:5432` — development;
- `localhost:5433` — e2e.

Базовый порядок:

```bash
docker compose up -d
pnpm install
cp apps/api/.env.example apps/api/.env
cd apps/api
pnpm prisma migrate dev
pnpm prisma db seed
cd ../..
pnpm --filter api start:dev
pnpm --filter web dev
```

## 11. Что ещё не является production-ready

- код-ревью стека безопасности — он смержен в `main` без единого ревью;
- реальный SMS-провайдер;
- реальный Kaspi/payment provider;
- объектное хранилище вместо локального диска;
- production deployment и оркестрация;
- централизованные логи, метрики и алерты;
- формализованные backup/restore;
- усиленная antifraud-защита;
- полноценная спецификация OpenAPI.

Закрыто стеком 26.07.2026: бесплатный пилотный режим (`CommercialMode`), rate limits
и security-заголовки, управление секретами (`config/environment.ts` с проверкой
`JWT_SECRET`), политика хранения персональных данных, каталог WebSocket-событий
([`WEBSOCKET_EVENTS.md`](./WEBSOCKET_EVENTS.md)), CI.
