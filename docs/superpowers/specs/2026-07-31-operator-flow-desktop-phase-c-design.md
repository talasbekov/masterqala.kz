# Оператор (desktop), Цикл B — Фаза C: Заказы + Журнал — дизайн-документ

## Контекст

Фаза A (каркас `apps/operator`, порт 4400, «Обзор») и Фаза B (Верификация, Пользователи, Мастера) реализованы, ревьюнуты, живьём проверены. Спека Цикла B: `docs/superpowers/specs/2026-07-30-operator-flow-desktop-design.md` — источники данных и общая архитектура зафиксированы там; этот документ детализирует UI/поведение для Фазы C: **Заказы** и **Журнал**. В отличие от Фаз A-B, оба раздела Фазы C не имеют mobile-first прообраза в `apps/web` — проверено (`grep` по `apps/web/src` не находит ни `admin/orders`, ни `admin/journal`), это полностью новая функциональность на фронте поверх уже готового Цикла A бэкенда.

Backend (не меняется в этой фазе):
- `GET /admin/orders?type=&status=&search=` — список (топ-100, без пагинации, без объединяющей обёртки — просто массив `AdminOrderRow[]`)
- `GET /admin/orders/:id?type=` — деталь (таймлайн, платежи, `canAssign`)
- `GET /admin/orders/:id/candidates?type=` — до 10 онлайн-кандидатов (только для `type=urgent`, только когда заказ в 3-й волне поиска >5 минут)
- `POST /admin/orders/:id/assign?type= {masterUserId}` — ручное назначение (404/409 на невалидного/занятого мастера, 409 на гонку)
- `GET /admin/journal?page=` — `{ rows: AuditLog[], total, page, pageSize: 30 }`, реальная серверная пагинация (единственный раздел панели с ней)

## Скоуп

**В скоупе:** разделы «Заказы» (список+фильтры+деталь с таймлайном+кандидаты+ручное назначение) и «Журнал» (список+пагинация) в `apps/operator`; общий словарь статусов заказов (`apps/operator/lib/orders.ts`, портирован из `apps/web/src/orderStatus.ts`) для консистентных пилюль статуса.

**Вне скоупа:** изменения `apps/api` (весь нужный бэкенд уже есть); реальный фильтр по периоду дат в «Заказах» (в прототипе есть, в API нет query для диапазона — не добавляется в этой фазе, см. «Решения» ниже); реальная пагинация списка заказов (бэкенд отдаёт top-100 без `page`, полагаемся на фильтры — решение уже зафиксировано в спеке Цикла B); поле «внутренний комментарий» оператора к заказу (декоративный элемент прототипа, нет соответствующего поля ни в `Order`/`PlannedOrder`, ни в ответе `detail()` — не добавляется); человеко-читаемый резолвинг сущностей в Журнале сверх статичного словаря `action → лейбл` (решение зафиксировано в спеке Цикла B).

## Раздел «Заказы»

**Источник данных:** `GET /admin/orders`, `GET /admin/orders/:id`, `GET /admin/orders/:id/candidates`, `POST /admin/orders/:id/assign` — все под query `type: 'urgent' | 'planned'`.

**Layout** (двухпанельный, как в прототипе — не узкий список карточек, как в «Верификации», а полноширинная таблица слева, т.к. записей до 100 и полей больше, чем помещается в карточку 300px):
- Заголовок «Заказы» + строка фильтров: тип (`все / срочные / плановые`), статус (dropdown, зависит от выбранного типа — объединённый список `STATUS_LABELS`+`PLANNED_STATUS_LABELS`, если тип «все»), поиск (debounce 400мс, по ID заказа или телефону клиента, серверный параметр `search`).
- Таблица слева (`flex-1`, колонки `ID | Тип | Клиент | Мастер | Категория | Статус`), каждая строка — кликабельная кнопка (паттерн `masters.tsx`/`users.tsx` grid-строк, но с `onClick`+подсветкой выбранной строки фоном `bg-fill-soft`, как выбранная карточка в `verification.tsx`).
- Панель деталей справа (фиксированные `400px`, паттерн `verification.tsx`): заголовок `#{id} · {category}` + пилюля статуса; адрес+район+дата создания; блок «Платежи» на `bg-fill-soft` — для `urgent` показывает Выезд/Сбор/Цену работы (`calloutPrice`/`serviceFee`/`workPrice`), для `planned` — Бюджет/Цену работы (`budget`/`workPrice`, без сбора — поля нет у планового режима); таймлайн (точка+время+событие, тот же визуальный паттерн, что уже даёт бэкенд списком `{at, event}` — рендерится как есть, без доп. логики на фронте).
- Если `detail.canAssign === true` — блок ручного назначения (см. ниже). Если `false` — блока нет вообще (не показываем задизейбленную кнопку без объяснения: сценарий возможен только для `urgent` в 3-й волне >5 мин, для всех остальных заказов кнопка была бы всегда неактивна и не несла бы смысла).

**Ручное назначение мастера (модалка со списком, не одна кнопка с зашитым именем — прототип рисует один кандидат в подписи кнопки, но реальный бэкенд отдаёт до 10; решение уже зафиксировано в спеке Цикла B §«Явные решения»: «показывать список всех кандидатов… оператор выбирает любого»):**
- Кнопка «Назначить мастера вручную» в панели деталей → по клику грузит `GET /admin/orders/:id/candidates?type=urgent` (лениво, не заранее — список актуален только в момент клика) → модалка (паттерн `users.tsx`: `fixed inset-0 bg-black/60` + `onClick stopPropagation` на внутреннем блоке).
- Модалка: список кандидатов `{name} · {distanceKm} км · онлайн`, каждый — кликабельная строка/кнопка «Назначить» рядом; пустой список → «Нет доступных кандидатов онлайн» без кнопок.
- Подтверждение — `POST /admin/orders/:id/assign?type=urgent {masterUserId}`; ошибки (404 «Мастер не найден», 409 «Мастер недоступен/уже занят», 409 «Заявка больше не в поиске») показываются прямо в модалке текстом, не закрывая её (кроме случая успеха).
- После успеха — закрыть модалку, рефетч детали заказа (`canAssign` станет `false`, появится назначенный мастер) и рефетч списка (статус строки обновится на ACCEPTED), плюс `refetchMetrics()` из `useOperatorMetrics()` — чтобы бейдж «Заказы» (`stuckSearches.length`) в сайдбаре пересчитался без ожидания 30-секундного поллинга (тот же паттерн, что уже применяется в `verification.tsx` после решения по анкете).

**Пилюли статуса** — новый модуль `apps/operator/lib/orders.ts` портирует `STATUS_LABELS`/`PLANNED_STATUS_LABELS` и вариант-функции из `apps/web/src/orderStatus.ts` дословно (лейблы), но с одним отступлением в маппинге цвета: `DISPUTE` рендерится через `warning`-токены (`bg-warning-bg`/`text-warning-ink`), а не `danger` — так делает прототип (мок «Спор» использует `#FFF1E8`/`#B4530A`, это ровно значения `--color-warning-bg`/`--color-warning-ink`), и семантически спор — это открытый процесс разбирательства, а не провал заявки (в отличие от `NO_MASTERS`/`CANCELLED_*`/`EXPIRED`, которые остаются `danger`). Остальные варианты — прямой перенос: `info`/`active` → `bg-fill-soft`/`text-primary`, `success` → `bg-success-bg`/`text-success-ink`, `danger` → `bg-danger-bg`/`text-danger`.

## Раздел «Журнал»

**Источник данных:** `GET /admin/journal?page=` → `{ rows, total, page, pageSize: 30 }`.

**UI:**
- Заголовок «Журнал» (без фильтров — прототип их не предусматривает для этого раздела, спека Цикла B тоже не требует).
- Таблица/список из трёх колонок (паттерн прототипа `130px 130px 1fr`): Время (`createdAt`, формат «сегодня ЧЧ:ММ» если сегодня, иначе «ДД.ММ ЧЧ:ММ») / Кто (`actor?.name ?? actor?.phone`, либо `'система'`, если `actorType === 'SYSTEM'`/`actor === null`) / Что (человеко-читаемый лейбл `action` из статичного словаря `ACTION_LABELS` + `comment`, если есть — формат `«{лейбл}: {comment}»`, либо просто лейбл, если `comment` пуст).
- Словарь `ACTION_LABELS` (все известные литералы `action`, см. таблицу ниже) — заводится в `apps/operator/lib/journal.ts`; для неизвестного будущего значения `action` (нет в словаре) — fallback показывает сам сырой `action` как есть, не падает.

| `action` | Лейбл |
|---|---|
| `MASTER_APPROVED` | Верификация: одобрено |
| `MASTER_REJECTED` | Верификация: отклонено |
| `MASTER_NEEDS_INFO` | Верификация: запрошены данные |
| `MASTER_AUTO_BLOCKED` | Мастер заблокирован автоматически |
| `USER_BLOCKED` | Пользователь заблокирован |
| `USER_UNBLOCKED` | Пользователь разблокирован |
| `ORDER_MANUALLY_ASSIGNED` | Заказ: ручное назначение мастера |
| `AUTO_CLOSED` | Заказ закрыт автоматически |
| `DISPUTE_RESOLVED` | Спор разрешён |

- Пагинация — реальная (единственный раздел с ней): кнопки «‹ Назад» / «Вперёд ›» под списком, задизейблены на границах (`page === 1` / `page * pageSize >= total`), подпись «Стр. {page} из {Math.ceil(total / pageSize)}» между кнопками. Смена страницы — обычный рефетч по `page`, без клиентского кеша предыдущих страниц.

## Решения по неоднозначностям прототипа

- **Фильтр «период»** — прототип показывает `период: сегодня ▾`, но `GET /admin/orders` не принимает диапазон дат. Не переносится в Фазу C (нет смысла держать декоративный select без реального эффекта); если понадобится — отдельный будущий пункт с изменением `apps/api`.
- **Кнопка ручного назначения с одним именем** → модалка со списком до 10 кандидатов (см. выше, решение уже было в спеке Цикла B, здесь только детализировано под реальную вёрстку).
- **«Внутренний комментарий»** (textarea в панели деталей заказа в прототипе) — не переносится: нет backend-поля для хранения, декоративный элемент, добавление потребовало бы миграции схемы вне скоупа этой фазы.
- **Цвет пилюли `DISPUTE`** — `warning` (оранжевый), а не `danger` (красный), вопреки классификации в `apps/web/src/orderStatus.ts` (там `DISPUTE → 'danger'`) — сознательное расхождение только в цвете пилюли для панели оператора, где важно визуально отличать «активный спор, требует разбора» от «заявка провалилась» (обе сейчас были бы одинаково красными). Лейблы статусов остаются те же, что в `apps/web`.
- **Журнал:** нет отдельного экрана/бейджа для «непрочитанных» записей — прототип и спека Цикла B не предполагают такого понятия для аудит-лога (в отличие от «Обзора», где есть счётчики требующих внимания).

## Тестирование и проверка

Как в Фазах A-B — нет фреймворка фронтенд-тестов. Верификация каждой задачи — `pnpm --filter operator build`; живая браузерная проверка (preview-тул) в конце фазы должна пройти: список заказов с фильтрами (тип/статус/поиск) → деталь урочной и плановой заявки (сверить разные блоки платежей) → зависшую в 3-й волне срочную заявку (нужно реально довести dev-заказ до `SEARCHING`+wave 3+возраст >5 мин, либо через прямой SQL/API — см. прецедент Фазы B «форсированный 409 через прямую SQL-гонку») → открыть модалку кандидатов → назначить → подтвердить статус ACCEPTED и рефетч бейджа «Заказы»; отдельно — «Журнал»: минимум 2 страницы записей (потребуется добрать >30 существующих `AuditLog`-строк в dev-БД, если их меньше — сгенерировать через уже пройденные операторские действия этой и прошлых фаз) + проверить лейбл «система» для `AUTO_CLOSED`/`MASTER_AUTO_BLOCKED`.
