# Дизайн: флоу мастера (десктоп, Next.js) — подпроект 3 из 4

Дата: 2026-07-29
Статус: утверждено пользователем в брейнсторминге, готово к плану реализации.

## Контекст

Подпроекты 1 (`apps/site`, публичные SEO-страницы) и 2 (`apps/client`,
клиентский флоу) завершены. Общий план из спеки подпроекта 1:
1) каркас+SEO (done), 2) клиентский флоу (done), **3) флоу мастера — эта
спека**, 4) оператор/админка. Мобильное приложение — отдельный трек после
завершения всех 4 веб-подпроектов, вне скоупа.

Роль мастера в текущем `apps/web` (React + Vite, mobile-first) — четыре
экрана: `WorkPage.tsx` (454 строки: онлайн/офлайн-присутствие, модалка
нового срочного оффера с таймером, состояния активной срочной заявки,
лента плановых заявок + форма ставки), `BecomeMasterPage.tsx` (анкета,
загрузка документов, статус верификации), `LeadCreditsPage.tsx` (баланс
и покупка пакетов кредитов), `WalletPage.tsx` (баланс и вывод средств).
Мастер — это тот же аккаунт, что и клиент (просто с `MasterProfile`), не
отдельная роль в `UserRole`. Общие для всех ролей экраны (Профиль,
Уведомления, История заказов) уже реализованы в `apps/client` (подпроект
2) — эта спека их не дублирует.

Бизнес-логика (стейт-машина заявки, матчинг, ставки, lead-кредиты,
кошелёк) полностью реализована на бэкенде (`apps/api`) и покрыта e2e-
тестами — эта спека не меняет бэкенд и не переизобретает логику, а
только переносит и перекомпоновывает фронтенд под десктоп.

## Продукт и платформа

Маркетплейс бытовых услуг «на дом» (Казахстан), два режима заявки —
срочный и плановый (см. `docs/product/spec.md`). Эта спека — личный
кабинет мастера: работа с заявками (срочными и плановыми), lead-кредиты,
кошелёк, анкета/верификация. Роль оператора — отдельный подпроект 4, вне
скоупа.

## Архитектура и границы

- Новый workspace-пакет **`apps/master`** — Next.js 15 (App Router), рядом
  с `apps/site`, `apps/client`, `apps/web`, `apps/api`, `packages/ui`.
- **Домен**: `master.masterqala.kz` — отдельный поддомен, разворачивается
  параллельно с `client.masterqala.kz` и `app.masterqala.kz` (старый
  `apps/web`, обслуживающий роль оператора до завершения подпроекта 4).
- **Рендеринг**: та же схема, что в `apps/client` — серверный корневой
  `layout.tsx` со статичным сайдбаром (список пунктов меню не зависит от
  данных пользователя, активный пункт подсвечивается клиентским island'ом
  через `usePathname`), все страницы `'use client'`, данные грузятся на
  клиенте.
- **Авторизация** — свой `/login` (SMS-OTP), JWT в `localStorage`,
  клиентский `useAuth()`-гард. `localStorage` не шарится между
  поддоменами — вход на `master.masterqala.kz` отдельный от
  `client.masterqala.kz`, тот же паттерн, что уже принят в подпроекте 2.
- **Бэкенд не меняется**: тот же `apps/api`, те же REST-эндпоинты и
  Socket.IO-события, что уже использует `WorkPage`/`BecomeMasterPage`/
  `LeadCreditsPage`/`WalletPage` в `apps/web` — новых эндпоинтов не
  требуется.
- **Связь с `apps/client`**: `apps/master` не дублирует Профиль,
  Уведомления и Историю заказов — сайдбар даёт обычную внешнюю ссылку
  «Личный кабинет клиента» → `client.masterqala.kz`.

## Маршруты и страницы

| Маршрут | Содержимое |
|---|---|
| `/login` | SMS-OTP вход (порт `apps/client/app/(auth)/login`) |
| `/` | Рабочий дашборд. **Гейт** (новое поведение — в `apps/web` этого нет: `/work` там открыт для любого авторизованного пользователя без проверки статуса анкеты): если анкета не в статусе `ACTIVE` — вместо ленты показывается карточка статуса заявки со ссылкой на `/become-master`; если `ACTIVE` — вкладки «Срочные»/«Плановые» |
| `/become-master` | Анкета: ФИО/ИИН/район/опыт/категории, статус (`PENDING_REVIEW`/`NEEDS_INFO`/`ACTIVE`/`REJECTED`), загрузка документов (порт `BecomeMasterPage`) |
| `/lead-credits` | Баланс + покупка пакетов кредитов (порт `LeadCreditsPage`) |
| `/wallet` | Баланс + вывод средств + история (порт `WalletPage`) |

Сайдбар: Работа (`/`) / Анкета (`/become-master`) / Lead-кредиты
(`/lead-credits`) / Кошелёк (`/wallet`) + внешняя ссылка «Личный кабинет
клиента» → `client.masterqala.kz`.

## Шелл: presence и глобальный оффер

Клиентский island в корневом layout — `MasterPresenceProvider`: держит
Socket.IO-соединение, online/offline-состояние (`presence:online`/
`presence:offline`, `geo:update` каждые 30с через `navigator.geolocation`,
порт логики `goOnline`/`goOffline` из `WorkPage`), слушает `offer:new`/
`offer:closed`/`order:status` **на уровне всего приложения**, не только
на `/`. `OfferOverlay` рендерится в layout поверх любой страницы —
входящий срочный оффер виден независимо от того, какая страница открыта
(desktop-отличие от мобильной версии, где подписка на `offer:new` жила
только пока смонтирован `WorkPage`). Модалка — центрированный диалог с
таймером и суммой компенсации (desktop-паттерн, не мобильный
full-screen takeover). «Принять» → переход на `/` с открытой вкладкой
«Срочные», где отображается принятая заявка.

## Активная срочная заявка

Карта слева на всю высоту (собственная копия Leaflet-обёртки по паттерну
`apps/client`: `MapViewInner.tsx` + `MapView.tsx` через
`next/dynamic({ ssr: false })`, т.к. Leaflet императивно трогает DOM) —
пин адреса клиента (статичный) + живая точка позиции мастера (источник —
те же координаты, что уже отправляются в `geo:update` каждые 30с, не
новый сокет-канал). Это desktop-расширение: в мобильной версии активная
заявка показывает только текстовый адрес и `tel:`-ссылку, без карты.

Справа — карточка статуса с действиями по стейт-машине (честный порт
`WorkPage`, без изменений в бизнес-логике):
- `ACCEPTED` → кнопка «Еду» (`POST /orders/:id/on-way`)
- `MASTER_ON_WAY` → кнопка «На месте» (`POST /orders/:id/on-site`)
- `INSPECTION` → форма цены+комментария (`POST /orders/:id/propose-price`)
- `AWAITING_PRICE_CONFIRM` → ожидание подтверждения клиентом
- `IN_PROGRESS` → кнопка «Выполнено» (`POST /orders/:id/complete`)
- `ACCEPTED`/`MASTER_ON_WAY` → доступна отмена с подтверждением
  (`POST /orders/:id/cancel`)

Телефон клиента — `tel:`-ссылка, как в оригинале.

**Уточнение (найдено при планировании Фазы 2, 2026-07-29):** бэкенд
нигде не отдаёт координаты адреса заявки — ни мастеру (`GET
/master/active-order`, `offer:new`), ни даже клиенту (`GET /orders/:id`).
`Order.location` (PostGIS `geography`) пишется при создании заявки, но
не читается обратно ни в одном эндпоинте — Prisma не может замапить
`Unsupported`-колонку через обычный `include`. Из-за этого у уже
смерженного подпроекта 2 `TrackView.tsx` пин назначения на карте сейчас
— захардкоженный центр Астаны (`{ lat: 51.1605, lng: 71.4704 }`), а не
реальный адрес клиента — скрытый баг, найденный только сейчас. Карта в
активной заявке мастера технически требует этих координат тем же
образом. Решение пользователя (AskUserQuestion): точечный бэкенд-фикс —
добавить `lat`/`lng` scalar-колонки на `Order` (по образцу
`Address.lat`/`Address.lng`), включить их в `ORDER_INCLUDE` и в
`offer:new`-пейлоуд `MatchingService`. Это нарушает пункт «бэкенд не
меняется» из этой спеки — сознательное, явно одобренное исключение,
т.к. без него карта из брейнсторминга технически невозможна. Тем же
фиксом попутно чинится баг `TrackView.tsx` в уже смерженном
подпроекте 2 (реальный адрес вместо Астаны по умолчанию) — включено в
Фазу 2 подпроекта 3 как связанная задача, а не отдельный цикл.

## Плановые заявки

Как и в клиентском плановом режиме (подпроект 2, фаза C) — в контракте
нет геоданных (только `district` — свободный текст), поэтому без карты,
узкая центрированная колонка (`max-w-[560px]`): лента карточек
(`GET /planned-orders/feed`, обновляется по сокетам `bid:closed`/
`planned:status`) → детали + форма ставки (цена/срок/комментарий,
`POST /planned-orders/:id/bids`). Учитывается `commercialMode`
(`FREE_PILOT` — отклик бесплатный, иначе списывается 1 lead-кредит) —
порт существующей логики без изменений.

## Lead-кредиты и кошелёк

`/lead-credits` — баланс + список пакетов с ценой, покупка (`POST
/lead-credits/purchase`). `/wallet` — баланс к выводу + форма вывода
(мин. 5000₸, `POST /wallet/withdrawals`) + история со статусами
(`PENDING`/`PAID`/`FAILED`). Обе страницы — честный порт с условным
рендером для случая `!leadCreditsEnabled`/`!payoutsEnabled` (бесплатный
пилот — кредиты/выплаты выключены на уровне `useCommercialMode()`).
Десктопная раскладка — по аналогии с `ProfilePage`/`AddressesPage`
подпроекта 2, точная компоновка (одна или две колонки) решается на
уровне плана реализации, архитектурно не значима.

## Анкета/верификация (`/become-master`)

Честный порт `BecomeMasterPage`: форма (ФИО, ИИН, район, опыт,
чекбоксы категорий из `GET /categories`) → `POST /masters/application`;
после подачи — карточка статуса с причиной отклонения/комментарием
доработки; загрузка документов (удостоверение, подтверждение
квалификации) через `POST /masters/application/documents`, доступна
пока статус `PENDING_REVIEW`/`NEEDS_INFO`. Единственное новое — на этой
странице теперь замыкается гейт `/`: как только статус становится
`ACTIVE`, рабочий дашборд открывается.

## Данные, ошибки

- Все данные и события — уже существующие эндпоинты/сокет-события
  `apps/api`, ни одного нового.
- Ошибки API (`propose-price`, `submit bid`, `purchase`, `withdrawals`,
  `application`) — inline-сообщения под формой, порт существующей
  обработки (`try/catch` → `setError(e.message)`).
- Гео-доступ отклонён браузером → предупреждение вместо тихого сбоя
  (порт `geoDenied` из `WorkPage`).
- Оффер протухает/закрывается (`offer:closed`) → модалка закрывается,
  показывается причина (порт `offerNote`).

## Фазы

**Фаза 1** — каркас: `apps/master` (layout, сайдбар, токены), `/login`,
`MasterPresenceProvider` + `OfferOverlay` (шелл-уровень, без реальных
действий над заявкой на этом этапе — только приём/просмотр оффера),
`/become-master` (анкета+документы+гейт для `/`).

**Фаза 2** — рабочий дашборд: presence-тумблер, активная срочная заявка
с картой и полной стейт-машиной, плановая лента+детали+ставки,
`/lead-credits`, `/wallet`.

## Тестирование

Без фреймворка юнит/e2e-тестов на фронте (тот же осознанный выбор, что и
в подпроектах 1-2 — визуальный слой, бэкенд не меняется). Проверка
вручную через dev-сервер и реальный браузер (см.
`docs/superpowers/specs/2026-07-28-client-flow-desktop-phase-b-design.md`
и `masterqala-local-dev-testing` — сид тестового мастера через прямой
SQL/`createActiveMaster`-паттерн): онлайн/офлайн-тумблер, приём оффера с
любой страницы приложения через глобальный overlay, полный цикл срочной
заявки (accept → on-way → on-site → propose-price → complete) с картой,
отдельно отмена; плановая лента → ставка → отображение в
`client.masterqala.kz` со стороны клиента; покупка lead-кредитов; вывод
из кошелька; подача анкеты + загрузка документов + просмотр статусов
(включая гейт `/` для неактивного мастера).

## Вне скоупа

- Профиль, Уведомления, История заказов как клиента — уже в
  `apps/client` (подпроект 2), эта спека их не переносит и не дублирует.
- Оператор/админка (верификация анкет, споры, выплаты) — подпроект 4.
- Мобильное приложение — отдельный трек после завершения всех 4 веб-
  подпроектов.
- Прод-деплой (`Dockerfile`, reverse proxy на реальном домене) —
  отдельная механическая задача.
