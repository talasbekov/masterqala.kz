# Оператор (desktop), Цикл B — Фаза B: Верификация, Пользователи, Мастера — дизайн-документ

## Контекст

Фаза A (`apps/operator`, порт 4400 — скаффолд, auth-шелл с гейтом по роли `OPERATOR`, сайдбар на 9 разделов, раздел «Обзор») реализована, ревьюнута, смержена в [PR #21](https://github.com/talasbekov/masterqala.kz/pull/21). Спека Цикла B: `docs/superpowers/specs/2026-07-30-operator-flow-desktop-design.md` — она уже определяет источники данных и общие решения для всех 9 разделов; этот документ детализирует UI/поведение конкретно для Фазы B: **Верификация**, **Пользователи**, **Мастера**.

Все три раздела используют уже существующий API — ни `apps/api`, ни схема Prisma в этой фазе не меняются:
- Верификация — `GET/POST /admin/applications` (существует до Цикла A, использовался старым `AdminListPage`/`AdminDetailPage` в `apps/web`)
- Пользователи — `GET/POST /admin/users` (Цикл A)
- Мастера — `GET /admin/masters` (Цикл A, **read-only** — мутаций над мастером в этом разделе нет)

## Скоуп

**В скоупе:** реализация всех трёх разделов в `apps/operator` — список+деталь+решение для Верификации, список+блокировка/разблокировка для Пользователей, read-only список с фильтрами для Мастеров; первая в проекте реализация реального просмотра авторизованных файлов (fetch+blob+lightbox) для документов верификации.

**Вне скоупа:** любые изменения `apps/api`; мутации над мастером в разделе «Мастера» (нет эндпоинта); реальная серверная пагинация (ни один из трёх эндпоинтов её не поддерживает — полагаемся на фильтры/поиск, тот же выбор, что уже принят для «Заказов» в Фазе A); бейджи в сайдбаре для этих трёх разделов (по спеке Цикла B бейджи есть только у Верификации/Заказов/Споров/Вывода — бейдж «Верификация» уже заведён в Фазе A через `/admin/metrics`, здесь ничего не меняется).

## Раздел «Верификация»

**Источник данных:**
- `GET /admin/applications?status=` — список: `{id, fullName, district, status, createdAt, user:{phone}, categories:[{category:{name,slug}}]}`
- `GET /admin/applications/:id` — деталь: то же + `iin`, `experienceYears`, `rejectionReason`, `documents:[{id,type,filePath,originalName,mimeType,sizeBytes,createdAt,scanStatus,scannedAt,cdrStatus}]`, `decisions:[{decision,comment,createdAt,operator:{name,phone}}]`
- `GET /admin/applications/:id/documents/:docId` — стримит файл (StreamableFile), требует `Authorization`-заголовок, `Content-Type` и `Content-Disposition` (`inline` для изображений, `attachment` для PDF) уже выставлены бэкендом
- `POST /admin/applications/:id/decision {decision: 'APPROVE'|'REJECT'|'REQUEST_INFO', comment?}` — `comment` обязателен, если `decision !== 'APPROVE'` (бэкенд валидирует, 400 без причины); 409, если документы ещё не прошли антивирус-скан (`scanStatus !== 'CLEAN'`); 409, если заявка уже не `PENDING_REVIEW`

**UI:**
- Заголовок + фильтр по статусу (`все / на проверке / нужны данные / активен / отклонён`) — клиентская фильтрация после одного `GET /admin/applications` без `status` (проще, чем рефетч на каждую смену фильтра, список анкет некрупный)
- Список слева (300px): карточка на анкету — имя + бейдж статуса + мета-строка (категории · «ждёт N дней/часов», вычисляется от `createdAt`)
- Панель деталей справа: имя + ИИН в заголовке, бейдж статуса; 4 плитки — Опыт (`experienceYears` лет), Категории, Геозона (`district`), Телефон (маскированный, как в прототипе — `+7 ··· XX XX` последние 4 цифры)
- Документы — плитки по `documents` (не фиксированные 3, как в прототипе, — ровно столько плиток, сколько строк вернул бэкенд), подпись = человеко-читаемая метка `type` из словаря `{ID_CARD: 'Удостоверение личности', QUALIFICATION: 'Подтверждение квалификации'}` (переиспользуется словарь `DOCUMENT_TYPES` из `apps/master/lib/masterApplication.ts:37-40`, а не изобретается заново — тот же набор типов, что мастер загружает в анкету); клик открывает **лайтбокс**
- Если анкета уже решена (`status` не `PENDING_REVIEW`) — вместо формы решения показывается баннер с результатом (текст зависит от `status`, как в прототипе: одобрен/отклонён/нужны данные) + видна последняя запись из `decisions` (комментарий оператора, кто принял)
- Если анкета `PENDING_REVIEW` — textarea комментария + 3 кнопки (Одобрить/Запросить данные/Отклонить); кнопки «Запросить данные»/«Отклонить» задизейблены, пока комментарий пуст (как валидирует бэкенд); под кнопками — подсказка «для отказа/запроса нужен комментарий», если применимо
- После успешного `POST .../decision` — рефетч и списка, и текущей анкеты (чтобы деталь сразу показала решённое состояние); рефетч также дёргает `refetch()` из `useOperatorMetrics()` (Фаза A), чтобы бейдж «Верификация» в сайдбаре обновился без ожидания 30-секундного поллинга

**Лайтбокс документа (новый паттерн для проекта — первая реальная авторизованная загрузка файла):**
- Клик по плитке → `fetch` на `/admin/applications/:id/documents/:docId` с `Authorization: Bearer <token>` (тем же `api()`-хелпером — потребуется вариант, возвращающий `Response`/`Blob`, а не `.json()`, см. план) → `URL.createObjectURL(blob)`
- Модальное окно поверх панели деталей: для `image/*` — `<img src={objectUrl}>` на весь модал; для `application/pdf` — открывается в новой вкладке (`window.open(objectUrl)`) вместо модалки (PDF неудобно рендерить инлайн без доп. библиотек, а браузер сам открывает PDF во вкладке)
- Закрытие модалки (или переход) — `URL.revokeObjectURL()`, чтобы не копить blob-URL в памяти
- Пока `fetch` идёт — спиннер/индикатор загрузки на плитке; при ошибке (404/403/сеть) — сообщение об ошибке на месте модалки, не падение всей страницы

## Раздел «Пользователи»

**Источник данных:** `GET /admin/users?search=`, `POST /:id/block {reason}`, `POST /:id/unblock`

**UI:**
- Поиск (debounce ~400мс) по телефону/имени → серверный `search`-параметр
- Таблица: Пользователь (имя + бейдж «заблокирован», если `isBlocked`) / Телефон / Роль (`клиент`/`клиент + мастер`, как отдаёт бэкенд) / Заказов / Действие
- «Заблокировать» → модалка: textarea причины (обязательна) + Подтвердить/Отмена; кнопка Подтвердить задизейблена, пока причина пуста
- «Разблокировать» → без модалки, сразу `POST /:id/unblock`
- После любого действия — рефетч списка (текущий поиск сохраняется)

## Раздел «Мастера»

**Источник данных:** `GET /admin/masters?category=&district=` — read-only

**UI:**
- Фильтры: категория (dropdown из `GET /categories`, уже используется в других разделах client/master), район (свободный текст или dropdown — см. Открытые вопросы)
- Таблица: Мастер (имя) / Категории (через запятую) / Рейтинг (`★ N.N` или `—`, если `rating: null`) / Заказов / Статус (`блокирован до …` / `активен · онлайн` / `активен · офлайн` — уже вычислено бэкендом, рендерится как есть)
- Без строчных действий — чисто обзорная таблица

## Решения по неоднозначностям прототипа

- **Типы документов** — `MasterDocument.type` — ровно два значения (`ID_CARD`, `QUALIFICATION`, сверено по `apps/master/lib/masterApplication.ts:37-40`), не три произвольные плитки прототипа. Раздел рендерит по одной плитке на каждую строку `documents`, подпись — из того же словаря меток, что уже использует анкета мастера.
- **Район в фильтре «Мастера»** — `district` в схеме свободнотекстовое поле (не enum, не FK). Используется простое текстовое поле ввода (не dropdown) — `GET /admin/masters?district=` ожидает точную строку (сверено по `admin-masters.service.ts` — `district: district ?? undefined` без `contains`), так что поле должно подсказывать оператору вводить район как есть в данных (например, «Есильский район»), не частичный текст.

## Тестирование и проверка

Как в Фазе A — нет фреймворка фронтенд-тестов, верификация задачи — `pnpm --filter operator build` + живая браузерная проверка через preview-тул в конце каждой задачи, требующей визуальной/интерактивной проверки. Для раздела «Верификация» живая проверка обязательно должна включать реальный просмотр хотя бы одного документа (не просто «плитка кликается»), чтобы подтвердить fetch+blob+lightbox работает сквозь реальный бэкенд с реальным JWT.
