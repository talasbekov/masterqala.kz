# Дизайн: клиентский флоу (десктоп, Next.js) — подпроект 2 из 4

Дата: 2026-07-28
Статус: утверждено пользователем в брейнсторминге, готово к плану реализации.

## Контекст

Подпроект 1 (`apps/site`, Next.js 15, публичные SEO-страницы) завершён — см.
`docs/superpowers/specs/2026-07-28-public-site-nextjs-design.md`. Общий план
из той спеки: 1) каркас+SEO (done), **2) клиентский флоу — эта спека**,
3) флоу мастера, 4) оператор/админка. Мобильное приложение — отдельный
трек после завершения всех 4 веб-подпроектов, вне скоупа.

Полнофункциональный клиентский флоу уже существует и работает в
`apps/web/src/features/client-v2` (React 19 + Vite, mobile-first PWA,
15 экранов, реализован в рамках отдельного цикла «клиент v2» летом 2026,
подробности — `docs/superpowers/specs/2026-07-19-client-v2-frontend-design.md`
и последующие фазовые спеки). Бизнес-логика (стейт-машины статусов заказа,
матчинг, ставки, диспуты, кошелёк, адреса) полностью реализована на бэкенде
(`apps/api`) и покрыта e2e-тестами — эта спека не меняет бэкенд и не
переизобретает логику, а только переносит и перекомпоновывает фронтенд под
десктоп.

## Продукт и платформа

Маркетплейс бытовых услуг «на дом» (Казахстан), два режима заявки —
срочный и плановый (см. `docs/product/spec.md`). Эта спека — авторизованный
личный кабинет клиента: заказ услуг, отслеживание статуса, диспуты,
кошелёк/платежи, адреса, уведомления, профиль, поддержка. Роли мастера и
оператора — отдельные подпроекты 3 и 4, вне скоупа.

## Архитектура и границы

- Новый workspace-пакет **`apps/client`** — Next.js 15 (App Router), рядом
  с `apps/site`, `apps/web`, `apps/api`, `packages/ui` в существующем pnpm-
  монорепо.
- **Домен**: `client.masterqala.kz` — отдельный поддомен, разворачивается
  параллельно с `app.masterqala.kz` (`apps/web`, обслуживающий роли мастера
  и оператора без изменений) до завершения подпроектов 3-4. Финальная схема
  доменов (cutover) — отдельное решение на будущее, вне этой спеки; сейчас
  фиксируем только то, что `apps/client` получает собственный поддомен и не
  проксируется через `apps/web`/`apps/site`.
- **Рендеринг — гибрид RSC-шелл + клиентский контент**: корневой
  `layout.tsx` — Server Component, статичная левая боковая панель (сайдбар,
  фиксированный список пунктов меню — не зависит от данных пользователя,
  только от факта авторизации; активный пункт подсвечивается клиентским
  island'ом через `usePathname`). Все 15 страниц — `'use client'`, данные
  грузятся на клиенте (`fetch` при монтировании/по действию). Next.js для
  контента используется как файловый роутер и бандлер, не как RSC-data-
  layer — сознательное упрощение, т.к. весь функционал приватный и
  персонализированный, а часть логики (Socket.IO, Leaflet-карта) физически
  клиентская.
- **Авторизация** — тот же паттерн, что в `apps/web`: JWT в `localStorage`,
  клиентский `useAuth()`-гард оборачивает все страницы кроме `/login` и
  редиректит неавторизованных. Никакого серверного middleware/cookie-based
  гарда — сознательное упрощение ради консистентности с существующим кодом
  и переносимости бизнес-логики без переписывания.
- **Бэкенд не меняется**: тот же `apps/api` — SMS-OTP авторизация, REST +
  Socket.IO (JWT в handshake). Новых эндпоинтов не требуется — backend-
  расширения для клиента v2 (фото, адреса, рейтинг, обогащённые ставки,
  геопозиция, приватность оффера и т.д.) уже реализованы в Цикле 1
  клиента v2.
- **Дизайн-система**: как и в `apps/site` — переиспользуются только CSS-
  токены брендинга (`packages/ui/src/tokens.css`: цвета, радиусы, шрифт
  Manrope). Мобильные React-компоненты `packages/ui` не переиспользуются
  напрямую (не подходят для широких десктопных сеток/таблиц) — новые
  desktop-примитивы (сайдбар, таблицы, двухколоночные раскладки) пишутся
  заново внутри `apps/client`.
- **i18n**: та же инфраструктура, что в `client-v2` — `react-i18next`, RU
  переводы копируются как рабочий базовый набор, KK/EN остаются заглушками
  (`fallbackLng: 'ru'`). Переключатель языка в `/profile` работает сразу.

## Страницы и маршруты

Прямое соответствие 15 экранам `apps/web/client-v2`, десктопная
перекомпоновка (сайдбар + широкий контент вместо центральной карточки на
узком экране), бизнес-логика переносится как есть:

| Маршрут | Экран | Десктопная перекомпоновка |
|---|---|---|
| `/login` | Вход (телефон → SMS-код) | Центрированная форма без сайдбара (до авторизации) |
| `/` | Главная | Виджеты в широком стеке вместо мобильных карточек |
| `/catalog` | Каталог категорий | Сетка 4-6 колонок вместо 2 |
| `/order/new` | Визард срочного заказа (4 шага: категория → описание+фото → адрес+карта → сводка) | Горизонтальный степпер сверху, карта и форма — бок о бок |
| `/order/:id` | Статус срочного заказа (7 видов: поиск/нет мастеров/трекинг/цена/прогресс/готово/закрыто) | Карта + детали заказа в 2 колонки |
| `/order/:id/dispute`, `/planned/:id/dispute` | Форма спора (общий `DisputePage`, `kind`-проп) | Форма + таймлайн статуса рядом |
| `/orders` | Мои заказы (вкладки Активные/История) | Таблица вместо списка карточек |
| `/planned/new` | Визард планового заказа (3 шага) | Как `/order/new` |
| `/planned/:id` | Статус планового заказа (ожидание ставок/активна/готово/закрыто) | Список ставок — сортируемая таблица |
| `/planned/:id/compare` | Сравнение ставок (до 5) | Полная сравнительная таблица без горизонтальной прокрутки |
| `/notifications` | Уведомления | Список шире, без изменений по сути |
| `/profile` | Профиль (язык, имя) | Форма в 2 колонки |
| `/addresses` | Адреса (CRUD) | Список + форма редактирования рядом, не полноэкранная модалка |
| `/payments` | Способы оплаты | Заглушка «скоро», как в мобильной версии (решение пользователя из Цикла 2 — реальное хранение карт не реализуется) |
| `/support` | Поддержка (FAQ + `tel:`) | Без изменений по сути |

## Данные, realtime, ошибки

- **Данные**: обычный `fetch` к тому же REST API `apps/api`, без
  TanStack Query/SWR (YAGNI, тот же паттерн, что в `client-v2` — простой
  `api.ts`-хелпер, переносится как есть).
- **Realtime**: `socket.io-client`, JWT в handshake, подписка на
  `master:location`/статусные события заказа — код переносится из
  `apps/web` почти без изменений. Контейнер карты (`MapView`, Leaflet)
  перестраивается на 2-колоночную раскладку (карта + детали заказа) вместо
  full-screen мобильного варианта.
- **Ошибки**: сетевые ошибки — тост/инлайн-сообщение с ретраем. Все action-
  хендлеры (отмена, повтор поиска, отправка ставки и т.п.) сразу оборачиваются
  в обработку ошибок — в `client-v2` пропущенные `.catch()` несколько раз
  находились постфактум в ревью, здесь закладываем сразу, а не откладываем.
  Несуществующий заказ/адрес по `:id` → страница «не найдено». Разрыв
  сокета — тихий реконнект без блокирующего UI.
- **Обработка похожих несостыковок прототип/бэкенд**: в процессе Цикла 2
  несколько раз всплывали точечные расхождения между версией фронтенда и
  реальным контрактом API (устаревшие поля, коды статусов, неверные пути
  переключения UI) — при переносе каждого экрана в `apps/client` сверять
  фактический ответ API, а не копировать типы из `client-v2` вслепую.

## Тестирование

Как и в `client-v2` — юнит/компонентных тестов на фронте в проекте
осознанно нет. Верификация: `pnpm --filter client build` на каждом
крупном шаге + живая браузерная проверка полного цикла на dev-сервере с
реальным `apps/api` (Postgres, Socket.IO): срочный заказ от визарда до
закрытия с оценкой, плановый заказ все статусы включая сравнение ставок и
выбор, открытие и разрешение спора, CRUD адресов, переключение языка в
профиле.
