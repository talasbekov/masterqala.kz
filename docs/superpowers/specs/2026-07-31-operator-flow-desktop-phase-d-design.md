# Оператор (desktop), Цикл B — Фаза D (последняя): Споры, Вывод средств, Безопасность — дизайн-документ

## Контекст

Фазы A (каркас+Обзор), B (Верификация/Пользователи/Мастера) и C (Заказы/Журнал) реализованы, ревьюнуты, финальные ревью чисты. Спека Цикла B: `docs/superpowers/specs/2026-07-30-operator-flow-desktop-design.md`. Фаза D — последняя из 4 фаз Цикла B: **Споры**, **Вывод средств**, **Безопасность**. После неё Цикл B (визуальный редизайн панели оператора) и весь подпроект 4 «Оператор/админка» завершены — это также последний из 4 подпроектов веб-редизайна под десктоп.

Бэкенд не меняется вообще (Споры и Вывод — уже существующий API, использовавшийся старым `apps/web`; Безопасность — существующий `admin/security/*` API, использовавшийся `AdminSecurityPage.tsx`, не входящий в 8 разделов хай-фай прототипа).

## Скоуп

**В скоупе:** три раздела в `apps/operator` — «Споры» (список+деталь с контекстом заказа+таймлайном+двухшаговое подтверждение решения), «Вывод средств» (read-only таблица+клиентский фильтр статуса), «Безопасность» (дашборд готовности+метрики+алерты с назначением/подтверждением/повтором доставки+последние audit-события — перенос `AdminSecurityPage.tsx` в новый шелл, с заменой `window.prompt()` на inline-форму комментария).

**Вне скоупа:** изменения `apps/api`; полноценный фильтруемый лог `/admin/security/events` (курсорная пагинация) — старая страница его не потребляла, спека Цикла B прямо требует перенос «как есть», не расширение; approve/reject вывода средств (бэкенд-эндпоинта нет — раздел был и остаётся read-only); реальный резолвинг `evidenceDocIds` в объекты с метаданными (API отдаёт только пути файлов).

## Раздел «Споры»

**Источник данных:**
- `GET /admin/disputes?status=` — список: сырые поля модели `Dispute` (`id`, `orderId`/`plannedOrderId`, `openedByRole`, `status`, `createdAt` и т.д.) — **без имени клиента/мастера и без категории заказа** (сервис не делает `include`). Список рендерит только то, что реально есть: `#{id.slice(0,8)} · Срочная/Плановая · открыл клиент/мастер · статус · «ждёт N ч»` — то же ограничение, что уже принято в mobile-first `AdminDisputesPage.tsx`, не выдумываем недостающие поля.
- `GET /admin/disputes/:id` — деталь: `reason`, `counterStatement`, `evidenceDocIds: string[]`, `openedByRole`, `status`, `orderId`/`plannedOrderId`, `commercialMode`.
- **Таймлайн заказа для контекстной панели (как в прототипе) через уже существующий `lib/orders.ts` (Фаза C, Task 1)** — `fetchOrder(id, type)`, где `type = dispute.orderId ? 'urgent' : 'planned'`, `id = dispute.orderId ?? dispute.plannedOrderId!`. Раздел «Споры» не дублирует парсинг таймлайна и не лезет в новый бэкенд-эндпоинт — переиспользует готовый `OrderDetail`/`OrderTimelineEvent` из Фазы C. Если `fetchOrder` вернёт 404 (заказ удалён/недоступен — маловероятно, но возможно) — контекстная панель показывает только то, что есть в самом споре, без таймлайна, без падения страницы.
- Фото-доказательства — тот же паттерн `Lightbox`, что в «Верификации» (Фаза B), но путь другой: `/disputes/${disputeId}/evidence/${encodeURIComponent(docId)}` (не `/admin/disputes/...` — сверено с бэкенд-сервисом, `getEvidenceStream` пропускает роль `OPERATOR` без проверки `guardParticipant`).
- `POST /admin/disputes/:id/resolve {refundServiceFee, penalizeMaster, resolutionNote}` — оба булевых поля обязательны, `resolutionNote` обязателен и непуст. 409 если спор уже не `OPEN`. Если `refundServiceFee=true` и возврат физически не удался — бэкенд уже разрешил спор (транзакция закоммичена) и вернёт `503 ServiceUnavailableException` с текстом «Спор разрешён, но возврат сбора не удался — требуется ручная сверка» — это не откат, UI должен показать это как отдельное предупреждение, а не как обычную ошибку формы (спор в БД уже `RESOLVED`, следующий рефетч детали это подтвердит).

**UI (двухпанельный, как «Верификация», но правая часть дополнительно делится на 2 подколонки — контекст + решение):**
- Список слева (300px) — карточки, как в «Верификации»: `#id · Срочная/Плановая`, статусный бейдж (открыт/решён), мета `открыл клиент/мастер · ждёт Nч`. Фильтр сверху: все/открыты/решены (серверный `status` query, рефетч при смене).
- Правая часть при выборе спора — сплит `flex-1` (контекст) + `w-[360px] shrink-0` (решение):
  - **Контекст** (`flex-1`): таймлайн заказа (из `fetchOrder`, если доступен) + блок «Заявление» (`reason`, кто открыл) + доказательства-плитки (клик → Lightbox) + блок «Пояснение второй стороны» (`counterStatement`, если есть — иначе «пояснение не предоставлено»).
  - **Решение** (`w-[360px]`, рендерится только если `status === 'OPEN'`; если `RESOLVED` — вместо формы баннер с итогом: `refundServiceFee`/`penalizeMaster` из уже сохранённого `dispute`, `resolutionNote`, дата разрешения):
    - Чекбокс «Вернуть сервисный сбор клиенту» — рендерится ТОЛЬКО если `dispute.orderId` существует И `commercialMode !== 'FREE_PILOT'` (для планового или FREE_PILOT спора чекбокса физически нет, как в mobile-first — вместо него для FREE_PILOT показывается поясняющий текст «В бесплатном пилоте сервисный сбор не взимался», для планового — ничего, платежный блок просто её не включает).
    - Чекбокс «Санкция мастеру» — всегда доступен.
    - `textarea` комментария решения (обязателен).
    - **Двухшаговое подтверждение** (новый UI-паттерн для проекта — прототип рисует его явно, готового аналога в кодовой базе нет): состояние `idle` → одна кнопка «Решить спор» (disabled + подсказка, если комментарий пуст) → клик переводит в состояние `confirming` — предупреждающий блок (`bg-warning-bg`/`text-warning-ink`) с текстовой сводкой выбранных чекбоксов («сбор будет возвращён» / «мастер получит санкцию» / оба / ни один) + «Действие необратимо и попадёт в журнал» + две кнопки: **«Подтверждаю решение»** (красная, реальный `POST resolve`) и **«Назад»** (возврат в `idle` без отправки, чекбоксы/комментарий сохраняются). После успеха — рефетч детали (покажет `RESOLVED`-баннер) + рефетч списка + `refetchMetrics()` (бейдж «Споры»). Если бэкенд вернул `503` (возврат не прошёл) — показать отдельным предупреждением поверх обновлённой (уже `RESOLVED`) детали: «Спор разрешён, но возврат сбора не удался — требуется ручная сверка», не как обычную ошибку формы.

## Раздел «Вывод средств»

**Источник данных:** `GET /admin/withdrawals` — read-only, без query-фильтров и пагинации на бэкенде. Возвращает `{id, masterUserId, amount, status, providerRef, requestedAt, paidAt, master: {phone: '<последние 4 цифры сырого номера>'}}`.

**UI:**
- Заголовок + клиентский (не серверный — бэкенд не поддерживает) фильтр по статусу (`все/в обработке/выплачено/отклонено`) — тот же паттерн, что «Верификация» применяет к своему `statusFilter` (клиентская фильтрация уже загруженного полного списка).
- Таблица (без панели деталей — плоский список, как в прототипе, не split-view): Мастер (телефон, т.к. имени в ответе нет) / Реквизиты (`+7 ··· XX XX`, форматирование из 4 голых цифр целиком на фронте — бэкенд большего не даёт) / Сумма (`{amount} ₸`) / Дата (`requestedAt`, `paidAt` если есть) / Статус-пилюля (`PENDING`→«в обработке»/warning, `PAID`→«выплачено»/success, `FAILED`→«отклонено · возврат»/danger — текст `FAILED` явно упоминает автовозврат, как в прототипе).
- Пояснительная строка внизу таблицы: «Выплаты проходят автоматически через платёжного провайдера; при отказе банка сумма возвращается на баланс мастера. Раздел read-only.» — дословно как в прототипе, без действий над строками.

## Раздел «Безопасность»

**Источник данных (весь уже существующий `admin/security/*` API, портируется из `AdminSecurityPage.tsx`):**
- `GET /admin/security/dashboard` — `{generatedAt, readiness, delivery, metrics, alerts (топ-10 открытых), recentEvents (топ-15)}`.
- `PATCH /admin/security/alerts/:id {status: 'ACKNOWLEDGED'|'RESOLVED', note?}`.
- `PATCH /admin/security/alerts/:id/assignment {assigneeUserId?: string|null}`.
- `POST /admin/security/alerts/:id/deliveries/retry`.
- `/admin/security/alerts` (полный курсорный список) и `/admin/security/events` (полный курсорный аудит-лог) **не подключаются** — старая страница их не использовала (только `dashboard.alerts`/`dashboard.recentEvents`, топ-N), спека Цикла B требует перенос «как есть», не новую функциональность.

**UI — перенос структуры `AdminSecurityPage.tsx` 1-в-1 (7 секций), с одним осознанным отступлением:**
1. Хедер + кнопка «Обновить» (ручной рефетч) + автополлинг каждые **15 секунд** (не 30, как на «Обзоре» — сохраняем оригинальный интервал этой страницы, она про безопасность, а не про общие метрики).
2. «Готовность»: бейдж READY/NOT READY, 4 карточки зависимостей (PostgreSQL/pg-boss/ClamAV/Alert webhook), список предупреждений.
3. 8 плиток метрик (открытые/просрочены подтверждение/просрочены решение/исчерпана доставка/заражено 24ч/ошибки скана 24ч/ожидают webhook/audit events 24ч).
4. Список «Открытые alerts» (топ-10 из dashboard) — карточки с цветовой индикацией severity (critical/high/warning → danger/warning/warning-мягче — см. решения ниже), бейджи (severity/status/`ESC L{level}`/повторения), мета (ответственный/последнее событие/дедлайны подтверждения-решения, красным если просрочено).
5. Кнопки на карточке alert: «Назначить себе» / «Снять» / «Принять» / «Повторить webhook» / «Закрыть» — те же условия рендера, что в оригинале.
6. Таблица «Последние audit events» (топ-15 из dashboard, три колонки: время/событие+уровень·исход/ресурс).
7. Футер «Обновлено: {generatedAt}».

**Осознанное отступление от буквального переноса — замена `window.prompt()`:** оригинал берёт комментарий подтверждения/решения через нативный `window.prompt()`. Для desktop-редизайна это заменяется на **inline-форму** тем же паттерном, что уже применяется в «Верификации»/«Спорах» этого проекта: клик по «Принять»/«Закрыть» разворачивает под карточкой конкретного алерта `textarea` (плейсхолдер «Комментарий — необязателен» для ack, «Комментарий решения» для resolve) + кнопки Подтвердить/Отмена, вместо мгновенной отправки. «Назначить себе»/«Снять»/«Повторить webhook» остаются без комментария (мгновенное действие, как в оригинале — им `window.prompt()` не требовался и там). Действие на одной карточке не блокирует остальные (тот же `actionId`-state, что в оригинале).

## Решения по неоднозначностям

- **Источник таймлайна спора** — переиспользуется `fetchOrder` из `lib/orders.ts` (Фаза C), не новый бэкенд-эндпоинт и не дублирование парсинга — единственный источник правды для таймлайна во всей панели оператора.
- **Двухшаговое подтверждение** — новый паттерн, спроектирован по прототипу дословно (warning-баннер с сводкой → красная кнопка финального действия либо «Назад»), т.к. в кодовой базе нет готового аналога (verification.tsx решает в один клик).
- **`window.prompt()` → inline-форма** — осознанное улучшение при переносе в desktop-шелл, консистентность с остальными разделами панели (нигде в `apps/operator` нет `window.prompt()`).
- **Вывод средств — клиентский фильтр статуса** — бэкенд не поддерживает query, полный список грузится один раз, фильтрация на фронте (тот же класс решения, что уже принят для «Мастеров»/«Заказов» там, где бэкенд не даёт нужный параметр).
- **Severity-цвета алертов** — `CRITICAL`→`danger`, `HIGH`→`warning`, `WARNING`→тоже `warning` (в токенах проекта нет отдельного «янтарного», оригинал использовал 3 оттенка через кастомные inline-стили — на токенах `@masterqala/ui` два ближайших семантических варианта `danger`/`warning` достаточно различимы, третий оттенок не заводится).

## Тестирование и проверка

Как в Фазах A-C — нет фреймворка фронтенд-тестов. Верификация каждой задачи — `pnpm --filter operator build`; живая браузерная проверка в конце фазы: как минимум один спор от открытия до двухшагового разрешения (с реальным фото-доказательством через Lightbox), таблица выводов с фильтром, и хотя бы один цикл alert (принять → назначить/переназначить → закрыть) в разделе «Безопасность» — если в dev-БД нет активных security-алертов, потребуется сначала сгенерировать хотя бы один (см. `apps/api/src/admin/security-observability.service.ts`/связанные правила — приемлемо создать вручную через прямой SQL-инсерт в `SecurityAlert`, аналогично прецеденту форсирования `canAssign` в Фазе C).
