# MasterQala: проект приведения MVP к Figma

Статус: проект архитектурных решений для ревью, не утверждённая реализация.
Источник: поручение владельца, ответы 13.10.2026 и [исходная сверка](../../audits/2026-10-13-figma-repository-baseline.md).

## Цель и ограничения

Реальный клиент создаёт заявку, мастер принимает, выезжает, осматривает, предлагает смету, получает согласие, начинает/завершает работу, клиент явно принимает результат. Расчёт напрямую мастеру; приёмка не подтверждает оплату. Web и mobile/PWA, ru/kk/en. Сохраняем NestJS/Prisma/PostGIS/pg-boss/Socket.IO, существующие приложения и packages/ui. Не меняем Figma, не внедряем неподтверждённую комиссию, не публикуем production.

Работа архитектурная: требуется миграция данных и контрактов. Начинаем с завершённого срочного сценария, затем плановый сценарий и сотрудники; это последовательные подпроекты, а не один неподъёмный PR.

## Подходы и рекомендация

1. Рекомендуется версионированная новая модель заказов в текущей архитектуре: новый режим DIRECT_PAYMENT и сохранённая версия lifecycle/dispatch. Новые заказы получают новые правила; старые PAID_MOCK/FREE_PILOT сохраняют финансовую историю и свои правила до отдельного решения. Цена — ветвление по версии и расширение типов, польза — нет переоценки существующих заказов.
2. Менять существующие enum/правила глобально проще по коду, но изменит поведение старых заказов и отложенных jobs. Допустимо только если подтверждено отсутствие реальных данных и согласован сброс тестовых данных. Сейчас это не подтверждено.
3. Новый backend или объединение всех фронтендов требует лишнего переписывания и не рекомендуется.

Все следующие технические решения — предложения. Два продуктовых решения (30 секунд и отмена 0/2500) уже утверждены.

## 1. Данные и контракт срочного заказа

Добавить новый коммерческий режим DIRECT_PAYMENT (флаги paymentsEnabled/leadCreditsEnabled/payoutsEnabled=false). Он описывает способ расчёта, не размер будущей комиссии. Существующие режимы и записи не переименовывать. Новые заказы сохраняют режим и lifecycleVersion=2; уже существующие записи — version=1. Не определять версию по текущему env.

Добавить PRICE_APPROVED между AWAITING_PRICE_CONFIRM и IN_PROGRESS; включить в active client/master predicates и raw SQL списки. `departedAt` фиксируется только успешным on-way. Добавить `materialsPrice`, `quoteVersion`, `consentedVersion`, `quoteApprovedAt`, `workStartedAt`, `cancellationAmount`. Суммы целые KZT, nonnegative, проверка безопасного диапазона и сумм на сервере. Точный верхний коммерческий лимит отдельно согласуется; технический лимит не выдавать за финансовую политику.

Переходы v2:
SEARCHING → ACCEPTED → MASTER_ON_WAY → INSPECTION → AWAITING_PRICE_CONFIRM → PRICE_APPROVED → IN_PROGRESS → DONE → CLOSED.

Отдельный POST start-work доступен только назначенному мастеру при PRICE_APPROVED и равенстве quoteVersion/consentedVersion. Согласование клиента передаёт ожидаемую quoteVersion; устаревшая версия получает 409 и свежий заказ. Новая/исправленная смета до старта увеличивает версию, сбрасывает согласие и возвращает AWAITING_PRICE_CONFIRM. Повторное согласование той же версии идемпотентно. Старые jobs не могут менять v2 автоматически. DONE активен для мастера до явной приёмки клиента. Приёмка идемпотентна для клиента этого заказа и не создаёт payment/accrual.

Смета возвращает отдельные строки работ/материалов/выезда и вычисленный total. 2500 в handoff — пример стоимости выезда в смете, тогда как фиксированная отмена 2500 утверждена явно. Чтобы не превратить пример в тариф, стоимость выезда в смете должна задаваться мастером и согласовываться вместе с остальными строками; окончательный способ задания этой строки требует решения владельца.

## 2. Последовательный подбор

Новые v2 заказы получают сохранённый dispatchMode=SEQUENTIAL. Учитываем категорию, ACTIVE/одобрение, блокировки, online presence, свободность и географию. Предложение получает только один ближайший подходящий мастер в текущей попытке. Окно 30 секунд, expiresAt сохраняется на сервере. Существующий радиус до 10 км сохраняется как техническая исходная граница, не новое обещание покрытия.

Решение: блокировка строки заказа в транзакции, выбор одного кандидата, создание оффера; очередь получает orderId/attempt/offerId. Повторный job переиспользует актуальный оффер; таймаут старого offerId/attempt no-op. Deadline проверяется сервером при accept. Назначение и таймаут используют одинаковую блокировку. Занятость мастера защищается отдельной блокировкой по masterUserId, чтобы два разных заказа не были приняты одновременно. На отказ/таймаут — следующий кандидат. При исчерпании — NO_MASTERS. При перезапуске воркера восстанавливается актуальная deadline-задача; frontend timer не принимает решений.

Отказ мастера от оффера отличается от отмены принятого заказа. Правила штрафов/переиспользования уже отменившего мастера не переносить из старых кредитов без согласования. До решения сохранять существующую фильтрацию отменившего этот заказ мастера и не начислять новые денежные санкции в v2.

## 3. Отмена и расчёт

До начала работ клиент может подтвердить отмену (включая осмотр, ожидание сметы, согласованную стоимость). В одной транзакции проверяется текущая стадия и departedAt, сохраняются отмена/причина/сумма и закрываются pending offers. Нет departedAt — 0 ₸, есть — 2500 ₸ напрямую мастеру. Работа и материалы не начисляются. Отмена не создаёт hold/capture/accrual/withdrawal и не получает автоматический paid.

На frontend подтверждение показывает серверный расчёт. При гонке с выездом/началом сервер отклоняет устаревший action и возвращает свежий заказ: нельзя незаметно согласиться на 2500 вместо показанного 0. После начала работ — обращение по существующему механизму, без нового обещания возврата/арбитража. Специфические решения городского партнёра остаются открытыми.

## 4. Интерфейс и локализация

packages/ui получает токены по фактическим контекстам Figma: Inter, #123B52, #FFE34A, светлые поверхности, 52 px основные действия и минимум 44 px hit target. Не менять глобально все приложения одним CSS-коммитом без проверки каждой поверхности. Изображения/иконки скачиваются из design context, сохраняются локально; screenshot не используется как готовый экран.

Состояния страниц отражают сервер. Back, переключение языка и отказ от диалога не меняют заказ. Не показывать empty до успешного ответа. Ошибка первоначальной загрузки имеет retry; stale данные при потере сети маркируются, мутации блокируются. Reconnect/foreground перечитывают заказ; защита от гонок ответов при смене ID.

Публичный сайт — актуальные split sections, реальные маршруты CTA, три языка. Клиент desktop — плавающий header/карта и боковая карточка для срочного flow; mobile — отдельная геометрия Figma без фиктивной системной status bar. Мастер — соответствующие действия по стадии. Не создавать фальшивую геолокацию/ETA вместо данных API.

Общий словарь ru/kk/en, интерполяции и plurals, даты/числа по локали, KZT без конвертации. Язык хранится локально/в профиле. Пользовательские тексты не переводить автоматически. Переводы казахского требуют языкового ревью; юридические тексты не считаются утверждёнными.

## 5. Плановый сценарий, сотрудники и push

Плановый flow сохраняет публикацию/отклики/выбор мастера, получает версионированную смету, отдельный старт и явную приёмку по общей политике v2. Точная матрица нового planned lifecycle определяется перед реализацией по актуальным design context.

Добавить ADMIN, оставить мастера как одобренный MasterProfile. Оператор управляет заказами/проверками/обращениями; admin — сотрудниками/доступами. Серверные права, подтверждения и append-only журнал. Создание первого администратора только явной процедурой, не автоматическим повышением всех операторов. Защита последнего активного admin атомарна. Доступ по городам/самостоятельные партнёры не добавляется без согласованных полномочий.

PWA: сохранение сессии, холодный запуск, permission после действия пользователя, отказ в push не блокирует приложение. Push содержит ID и открывает актуальный заказ через авторизацию; не меняет статус. Backend subscriptions, VAPID secrets через env, очистка недействительных подписок, тесты доступа. HTTPS и реальные устройства — отдельная эксплуатационная проверка.

## Приёмка и безопасность миграции

Тестировать real PostgreSQL/PostGIS и pg-boss (часть интеграционных тестов с очередью включённой), гонки двух мастеров/двух заказов, redelivery/перезапуск, старые jobs, устаревшую смету, отмену одновременно с выездом, повторную приёмку, 403 чужого заказа, переключение языков и cold start. Legacy tests остаются зелёными. Данные сначала расширяются additive migration, затем разворачивается совместимый backend/frontend. Удаление старых таблиц и финансовой истории не входит в задачу.

## Решения перед первой миграцией

1. Подтвердить предложенное сохранение старых заказов и новый режим DIRECT_PAYMENT для новых.
2. Определить выезд в смете: фиксированные 2500 или строка, которую мастер задаёт и клиент согласует. Фиксированная отмена 2500 уже согласована и не зависит от этого выбора.
3. Дать доступную тестовую PostgreSQL/PostGIS или выполнять проверку CI после создания PR. Production БД для тестов не использовать.

Комиссия, решения споров, полномочия партнёров, юридические условия и SMS-провайдер остаются отдельными вопросами; независимую UI/CI работу можно выполнять без них.
