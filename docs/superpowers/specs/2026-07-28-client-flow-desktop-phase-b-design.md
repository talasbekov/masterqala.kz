# Дизайн: клиентский флоу (десктоп) — Фаза B: срочный режим

Дата: 2026-07-28
Статус: утверждено пользователем в брейнсторминге, готово к плану реализации.

## Контекст

Фаза A подпроекта 2 (`apps/client` — каркас Next.js 15, RSC-шелл с левым
сайдбаром, клиентский auth-гард, `/login`, `/`, `/catalog`) реализована,
ревьюнута и завершена 2026-07-28 — см.
`docs/superpowers/specs/2026-07-28-client-flow-desktop-design.md` (общая
спека подпроекта 2, таблица всех 15 маршрутов) и
`docs/superpowers/plans/2026-07-28-client-flow-desktop-phase-a.md`.

Эта спека — Фаза B: срочный режим заявки. Источник для переноса —
`apps/web/src/features/client-v2/` (мобильный React+Vite клиент,
полностью рабочий, покрыт e2e-тестами на бэкенде): `components/MapView.tsx`
(93 строки, императивный Leaflet), `pages/NewOrderPage.tsx` (385 строк,
визард срочной заявки, 4 шага), `pages/OrderPage.tsx` (98 строк, тонкий
статус-driven шелл) + `components/order-views/{SearchView, NoMastersView,
TrackView, PriceView, ProgressView, DoneView, ClosedView}.tsx` (7 файлов),
`pages/DisputePage.tsx` (158 строк, общий компонент для срочного и
планового спора через проп `kind`).

Бизнес-логика (стейт-машина статусов заявки, матчинг, ценообразование,
диспуты) полностью реализована на бэкенде (`apps/api`) и покрыта
e2e-тестами — эта спека не меняет бэкенд, только переносит и
перекомпоновывает фронтенд под десктоп, как и Фаза A.

## Архитектура и зависимости

- **Новая зависимость `apps/client`**: `leaflet` (не `react-leaflet` —
  оригинал использует «сырой» Leaflet императивно через `useRef`/
  `useEffect`; `react-leaflet` числится в `apps/web/package.json`, но
  реально не используется нигде — известный хвост из бэклога прошлого
  цикла, не тащим его в новый пакет).
- **`MapView`**: логика карты выносится в `MapViewInner.tsx` и
  оборачивается через `next/dynamic(() => import('./MapViewInner'), {
  ssr: false })` в `MapView.tsx`. Leaflet обращается к `window`/DOM на
  уровне конструктора карты; Next.js всё равно один раз рендерит клиентские
  компоненты на сервере перед гидратацией (тот же класс нюанса, что уже
  решался для `AuthGuard` в Фазе A другим приёмом) — для карт правильное и
  стандартное решение — полностью пропустить серверный рендер именно этого
  поддерева через `next/dynamic({ ssr: false })`, а не городить SSR-гварды
  внутри самого компонента.
- **`apiUpload`/`waitForUploadScan`** переносятся в `apps/client/lib/api.ts`
  один в один из `apps/web/src/api.ts` (сознательно не перенесены в Фазе A
  за ненадобностью — только сейчас появляется первый потребитель:
  фото заявки и доказательства спора). Логика (в т.ч. поллинг статуса
  антивирусной проверки `PENDING_SCAN`/`SCANNING`/`CLEAN`/`INFECTED`/
  `SCAN_FAILED` с таймаутом 30с) переносится без изменений.
- **`DisputeView`**: переиспользуемый компонент (ex-`DisputePage`) с
  пропом `kind: 'orders' | 'planned-orders'`, идентичным оригиналу.
  Тонкая страница-обёртка `app/(app)/order/[id]/dispute/page.tsx`
  рендерит `<DisputeView kind="orders" />`. Плановая обёртка
  (`app/(app)/planned/[id]/dispute/page.tsx`, `kind="planned-orders"`)
  добавится в Фазе C без единой правки в `DisputeView`.
- **Динамические маршруты**: `[id]`-параметр читается через `useParams()`
  из `next/navigation` (клиентский хук, прямой аналог
  `useParams<{id:string}>()` из `react-router-dom` — работает в клиентских
  компонентах без `await`, в отличие от серверных, где `params` — Promise).
- **Навигация**: `useNavigate()` → `useRouter()` (`next/navigation`),
  `navigate(-1)` → `router.back()`, `<Link to=...>` → `<Link href=...>`
  (те же правила адаптации, что в Фазе A).

## Раскладка визарда `/order/new`

Широкий 2-колоночный кадр на всех 4 шагах: степпер+заголовок на всю ширину
сверху, ниже — левая колонка (контент шага, ~560px) и правая колонка
(карта, один и тот же `MapView`-инстанс на все 4 шага — меняются только
пропы, не пересоздаётся):

- **Шаг 1 (категория)** и **Шаг 2 (описание+фото)**: карта справа
  статична — `mode="pin"`, `onCenterChange` не передаётся, центр — уже
  полученная геопозиция (`geo`, из `navigator.geolocation` при монтировании
  страницы, без изменений). Чисто визуальный якорь, без интерактива.
- **Шаг 3 (адрес)**: карта справа интерактивна — `mode="pin"` с
  `onCenterChange={setGeo}`, как в оригинале. Форма адреса (текстовое
  поле, сохранённые адреса, подъезд/этаж/квартира, район, комментарий) —
  без изменений логики, только раскладка (левая колонка вместо полной
  ширины).
- **Шаг 4 (сводка)**: карта справа снова статична (финальная точка после
  шага 3), слева — сводка заказа, предпросмотр цены (`POST
  /orders/preview`), способ оплаты (заглушка), кнопка отправки.

## Раскладка `OrderPage` (статус-driven экраны)

- **`SearchView`/`TrackView`** (используют карту): 2 колонки — карта слева
  на всю высоту контентной области (`mode="pulse"`/`"tracking"`
  соответственно), справа — карточка-панель (`rounded-lg border
  border-border bg-surface p-4` вместо мобильных `rounded-t-sheet
  shadow-sheet`, которые были специфичны для нижней шторки и не нужны в
  раскладке из двух колонок). Внутреннее содержимое панели (таймер волны +
  кнопка отмены в `SearchView`; аватар/рейтинг/ETA/звонок/отмена в
  `TrackView`) переносится без изменений — меняется только контейнер
  вокруг него.
- **`NoMastersView`/`PriceView`/`ProgressView`/`DoneView`/`ClosedView`**
  (карта не используется): узкая центрированная колонка (`mx-auto
  max-w-[560px]`), без изменений раскладки относительно оригинала — эти
  экраны одинаково хорошо смотрятся как центрированная форма/сообщение и
  на мобильном, и на десктопе.

## `/order/:id/dispute`

Узкая центрированная колонка (`mx-auto max-w-[560px]`, как форма) — форма
причины спора + таймлайн статуса, картой не пользуется. Десктопная
перекомпоновка минимальна: контейнер перестаёт растягиваться на всю
ширину экрана, логика/вёрстка полей — без изменений.

## Данные, сокеты, ошибки

- **Данные**: те же эндпоинты, что уже использует `apps/web` (все уже
  реализованы в `apps/api`, ничего нового не создаётся) — `GET
  /categories`, `GET /addresses`, `POST /orders/preview`, `POST /orders`,
  `GET /orders/:id`, `POST /orders/:id/{cancel, retry-search,
  confirm-price, reject-price, confirm-completion, review}`, `POST
  /uploads`, `POST /orders/:id/disputes`, `POST /disputes/:id/evidence`.
- **Realtime**: `order:status` (перезагружает заявку на любой смене
  статуса — подписка живёт в шелле `OrderPage`, не в отдельных видах) и
  `master:location` (только в `TrackView` — обновляет позицию мастера на
  карте и ETA). Тот же `getSocket()` из `apps/client/lib/socket.ts`
  (Фаза A), без изменений.
- **Ошибки**: тот же паттерн, что в Фазе A и в оригинале — инлайн
  `text-danger`-сообщение + retry-кнопка там, где применимо. Загрузка
  фото — `uploading`-состояние блокирует повторный выбор файла на время
  загрузки+проверки; ошибка антивирусной проверки или таймаут всплывает
  как обычная ошибка формы (текст из `waitForUploadScan`).

## Тестирование

Юнит-тестов на фронте нет (та же осознанная практика, что в Фазе A) —
верификация каждой задачи через `pnpm --filter client build`. Финальная
задача фазы — живая браузерная проверка полного цикла срочной заявки:
визард (все 4 шага, включая загрузку фото) → поиск мастера → мастер
принимает и передвигается (через прямые API/сокет-вызовы за мастера, т.к.
редизайна роли мастера ещё нет — подпроект 3, не эта фаза) → трекинг на
карте с ETA → согласование цены → прогресс со степпером → готово →
подтверждение выполнения + оценка звёздами → отдельно: открытие спора на
другой заявке.

## Вне скоупа

- Плановый режим (`/planned/*`) — Фаза C.
- История заказов, профиль, адреса, поддержка, платежи — Фаза D.
- Редизайн ролей мастера/оператора — подпроекты 3 и 4.
- Реальный Kaspi вместо мок-провайдера — не менялся с прошлых циклов.
- `react-leaflet` — сознательно не добавляется (не используется даже в
  оригинале, несмотря на присутствие в `package.json` `apps/web`).
