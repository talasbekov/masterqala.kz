# Оператор (desktop), Цикл B — визуальный редизайн панели: дизайн-документ

## Контекст

Цикл A (бэкенд) подпроекта 4 «Оператор/админка» веб-редизайна завершён и смержен ([PR #21](https://github.com/talasbekov/masterqala.kz/pull/21)): добавлены `/admin/orders` (список/деталь/кандидаты/ручное назначение), `/admin/metrics` (агрегаты дашборда), `/admin/journal` (аудит-журнал) и точки записи `AuditLog` во все существующие операторские решения и системные авто-события. Три раздела прототипа (Верификация, Споры, Вывод средств) уже полностью покрыты существующим API (`/admin/applications`, `/admin/disputes`, `/admin/withdrawals`) — их бэкенд не менялся ни в Цикле A, ни в этом цикле.

Хай-фай прототип: `apps/MasterQala/design_handoff_masterqala/Этап 6 - Оператор (desktop).dc.html` (8 разделов: Обзор, Верификация, Пользователи, Мастера, Заказы, Споры, Вывод средств, Журнал). Прототип использует ту же палитру, что уже определена в `packages/ui/src/tokens.css` (`--color-primary: #166088`, `--color-border: #C0D6DF`, `--color-danger: #DC2626`, `--color-success: #059669`, шрифт Manrope, радиусы 10/14/18px) — палитры не расходятся, отдельного набора токенов заводить не нужно.

Оригинальная спека Цикла A предполагала пересобрать панель внутри `apps/web` (старый Vite mobile-first стек). С тех пор подпроекты 2 (`apps/client`) и 3 (`apps/master`) установили другой прецедент — отдельное Next.js 15 приложение на своём порту под каждую роль. Решение этого брейнсторминга: следовать новому прецеденту, не старой спеке Цикла A.

Также в `apps/web` существует `AdminSecurityPage.tsx` (377 строк) — security/observability дашборд (health/readiness, алерты, аудит безопасности), не входящий в 8 разделов хай-фай прототипа. Решение: добавить его как 9-й раздел новой панели, перенеся визуально в новый шелл.

## Скоуп

**В скоупе:** новое приложение `apps/operator`, все 9 разделов (8 из прототипа + Безопасность), полная замена текущих голых `apps/web`-страниц (`AdminListPage`, `AdminDetailPage`, `AdminDisputesPage`, `AdminDisputeDetailPage`, `AdminWithdrawalsPage`, `AdminSecurityPage` — все удаляются после переноса, вместе с роутами `/admin/*` и `RequireOperator` в `apps/web/App.tsx`).

**Вне скоупа:** любые изменения в `apps/api` (весь нужный бэкенд уже есть — Цикл A + существующие эндпоинты); мутации над мастером в разделе «Мастера» (Цикл A не давал такого эндпоинта — раздел read-only); реальная пагинация в «Заказах» (бэкенд отдаёт топ-100 без `page`, это остаётся так — см. ниже); WS/realtime-уведомления оператору (по спеке Цикла A — не в этом цикле); человеко-читаемый резолвинг сущностей в Журнале (см. ниже); i18n (панель — только RU, как и `apps/master`).

## Архитектура

Новое приложение `apps/operator` (Next.js 15, порт **4400**) — точная копия прецедента `apps/client`/`apps/master`:

- **Auth:** `AuthProvider`+`AuthGuard` (JWT в `localStorage['token']`, редирект на `/login` без юзера) + дополнительная проверка роли — гейт пускает только пользователей с ролью `OPERATOR`, иначе редирект на `/login` с сообщением об отсутствии доступа (аналог `RequireOperator` из `apps/web`, но как часть `AuthGuard`).
- **Шелл:** Server Component root/`(app)`-layout + клиентский `Sidebar` (9 пунктов навигации, статично отрендеренных, без динамического меню) + `main` с `AuthGuard`. Стили — инлайновый Tailwind на токенах `@masterqala/ui` (`bg-primary`, `border-border`, `text-ink-soft` и т.д.), без общей библиотеки компонентов (Button/Card и т.п. не создаются в этом цикле — YAGNI, следуем прецеденту `apps/client`/`apps/master`, где их тоже нет).
- **API-клиент:** `lib/api.ts` — идентичный паттерн (`NEXT_PUBLIC_API_URL`, JWT из `localStorage`, единый `handle()` для ошибок).
- **i18n:** отсутствует (только RU, как `apps/master`).
- **Realtime:** отсутствует — панель обновляет данные по интервалу (для дашборда/зависших заказов, напр. каждые 30с) и явным рефетчем после мутирующих действий (блокировка, назначение, решение спора, ack/resolve алерта). Соответствует явному решению спеки Цикла A: «WS для оператора — не в этом цикле».
- **CORS:** добавить `http://localhost:4400`, `http://127.0.0.1:4400` в `CORS_ORIGINS` (`apps/api/.env`, `apps/api/.env.example`, `docs/DEPLOYMENT_RUNBOOK.md`).

## Разделы и источники данных

Бэкенд не меняется — весь нужный API уже существует (Цикл A + `/admin/applications`/`/admin/disputes`/`/admin/withdrawals`/`/admin/security/*`).

| Раздел | Источник данных | Поведение |
|---|---|---|
| **Обзор** | `GET /admin/metrics` | 4 карточки «требует внимания» (`stuckSearches.length`, `openDisputesCount`, `pendingVerificationCount`, `pendingWithdrawalsCount`) + 4 обычные метрики (`activeUrgentCount`, `publishedPlannedCount`, `foundMasterRate`, `medianSearchSeconds`) + таблица «поиск без мастера» (`stuckSearches`), клик по строке → переход в деталь заказа (раздел Заказы) |
| **Верификация** | `GET/POST /admin/applications` (существующий) | Список анкет (слева) + деталь (справа): документы, комментарий, approve/needsInfo/reject |
| **Пользователи** | `GET/POST /admin/users` | Поиск по телефону/имени, блокировка/разблокировка с обязательной причиной |
| **Мастера** | `GET /admin/masters` | Read-only список с производным статусом (блокирован/приоритет↓/активен-онлайн/активен-офлайн) |
| **Заказы** | `GET /admin/orders`, `GET /:id`, `GET /:id/candidates`, `POST /:id/assign` | Список (топ-100 от бэкенда, без пейджера — фильтры тип/статус/период/поиск должны быть достаточны, чтобы сузить список до разумного размера) → деталь с таймлайном и сводкой платежей → для зависших urgent-заявок (`canAssign`) — список всех кандидатов (до 10, дистанция+онлайн-статус) → ручное назначение |
| **Споры** | `GET/POST /admin/disputes` (существующий) | Список → контекст заказа (таймлайн, заявление сторон, фото) → чекбоксы возврат сбора / санкция мастеру → обязательный комментарий → двухшаговое подтверждение (как в прототипе) |
| **Вывод средств** | `GET /admin/withdrawals` (существующий) | Read-only список, телефон маскирован |
| **Журнал** | `GET /admin/journal?page=` | Единственный раздел с настоящей пагинацией (бэкенд её поддерживает) |
| **Безопасность** | `GET/POST /admin/security/*` (существующий, портируется из `AdminSecurityPage.tsx`) | Health/readiness, алерты (ack/assign/retry), аудит-события безопасности — переносится как есть в новый визуальный шелл |

Бейджи-счётчики в сайдбаре (Верификация/Заказы/Споры/Вывод — как в прототипе) считаются из уже загруженного на Обзоре `/admin/metrics`, без отдельных запросов на каждый бейдж.

### Явные решения по неоднозначностям прототипа

- **Ручное назначение мастера:** прототип показывает одну кнопку с одним кандидатом («Айбек Т. · 1.8 км · онлайн»), но `GET /admin/orders/:id/candidates` возвращает до 10. Решение: показывать список всех кандидатов в панели деталей заказа, оператор выбирает любого (не только первого).
- **Пагинация «Заказов»:** бэкенд отдаёт топ-100 строк без `page`-параметра. Решение: не трогать `apps/api`, убрать пейджер из UI в этом цикле, полагаться на фильтры (тип/статус/период/поиск), чтобы список оставался разумного размера.
- **Журнал без резолвинга сущностей:** `AuditLog` хранит `action`/`targetId`/`comment`, не готовое предложение; `targetId` не всегда резолвится в одну и ту же сущность единообразно для одного `targetType` (унаследованная нестыковка из Цикла A: `MASTER_AUTO_BLOCKED` кладёт `User.id`, `MASTER_APPROVED` — `MasterProfile.id`, оба под `targetType: MASTER_PROFILE`). Решение: не резолвить имена сущностей (это N+1 запросов на каждую строку журнала) — показывать статичный словарь `action → человеко-читаемая метка` («Верификация: одобрено», «Пользователь заблокирован» и т.п.) + комментарий + имя/телефон актёра (уже приходят из бэкенда через `actor`-relation) + сокращённый `targetId`. Полный резолвинг сущностей — в бэклог.

## Декомпозиция на фазы

По прецеденту client v2/master — каждая фаза получает свой mini-plan через `superpowers:writing-plans` непосредственно перед реализацией:

- **Фаза A** — скаффолд `apps/operator` (auth-шелл с проверкой роли, sidebar на 9 пунктов, `api.ts`, CORS) + **Обзор** — первый вертикальный срез через реальный API, устанавливает паттерны для всех остальных фаз.
- **Фаза B** — **Верификация + Пользователи + Мастера** — три однотипных раздела «список → деталь/действие».
- **Фаза C** — **Заказы** (список+деталь+кандидаты+ручное назначение) **+ Журнал** (тот же паттерн таймлайна, что и деталь заказа/спора).
- **Фаза D** — **Споры + Вывод средств + Безопасность** — споры с самым насыщенным флоу решения; вывод и безопасность — завершающие, более простые/переносимые разделы.

## Тестирование и проверка

Как в `apps/client`/`apps/master` — во фронтенд-приложениях проекта нет фреймворка тестов (осознанная практика). Верификация каждой задачи — `pnpm --filter operator build`; живая браузерная проверка (preview-тул) в конце каждой фазы. Финальный whole-cycle review (opus) после всех 4 фаз — по прецеденту Цикла 2 клиента v2.
