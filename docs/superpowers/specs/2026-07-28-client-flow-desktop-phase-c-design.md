# Дизайн: клиентский флоу (десктоп) — Фаза C: плановый режим

Дата: 2026-07-28
Статус: утверждено пользователем в брейнсторминге, готово к плану реализации.

## Контекст

Фазы A (каркас) и B (срочный режим) подпроекта 2 (`apps/client`) реализованы
и завершены — см. `docs/superpowers/specs/2026-07-28-client-flow-desktop-design.md`
(общая спека, таблица маршрутов) и
`docs/superpowers/specs/2026-07-28-client-flow-desktop-phase-b-design.md`.

Эта спека — Фаза C: плановый режим заявки. Источник для переноса —
`apps/web/src/features/client-v2/` (мобильный клиент): `pages/PlannedNewOrderPage.tsx`
(визард), `pages/PlannedOrderPage.tsx` (статус-driven шелл),
`pages/PlannedComparePage.tsx`, `components/planned-order-views/{PlannedDoneView,
PlannedClosedView}.tsx`. Архитектурные решения дизайна планового режима как
такового (маршруты, карта статус→вид, контракты) зафиксированы ранее в
`docs/superpowers/specs/2026-07-20-client-v2-phase-c-design.md` (мобильный
цикл «клиент v2», Фаза C) и здесь не пересматриваются — эта спека только
описывает десктопную перекомпоновку, аналогично тому, как Фаза B десктопа
адаптировала мобильную Фазу B.

Бэкенд (`apps/api`) не меняется.

## Ключевое отличие от Фазы B: карты нет вообще

Плановый режим не использует геопозицию — `CreatePlannedOrderDto` не
принимает `lat`/`lng`, адрес вводится текстом. Поэтому здесь нет
десктопной 2-колоночной раскладки «форма + карта», которая определяла
Фазу B. По решению пользователя (брейнсторминг) — **везде узкая
центрированная колонка** (`mx-auto max-w-[560px]`), тот же паттерн, что
уже используют в Фазе B экраны без карты (`NoMastersView`, `PriceView`,
`ProgressView`, `DoneView`, `ClosedView`). Единственное исключение —
таблица сравнения ставок (см. ниже).

## Маршруты

| Маршрут | Страница Next.js | Источник (мобильный) |
|---|---|---|
| `/planned/new` | `app/(app)/planned/new/page.tsx` | `PlannedNewOrderPage.tsx` |
| `/planned/[id]` | `app/(app)/planned/[id]/page.tsx` | `PlannedOrderPage.tsx` |
| `/planned/[id]/compare` | `app/(app)/planned/[id]/compare/page.tsx` | `PlannedComparePage.tsx` |
| `/planned/[id]/dispute` | `app/(app)/planned/[id]/dispute/page.tsx` | тонкая обёртка `<DisputeView kind="planned-orders" />` |

`DisputeView` (Фаза B) уже принимает проп `kind` без изменений — обёртка
пишется по образцу существующей `app/(app)/order/[id]/dispute/page.tsx`
(`kind="orders"` → `kind="planned-orders"`).

Карта `plannedOrder.status` → вид (без изменений от мобильной спеки):
`PUBLISHED`→pwait, `MASTER_SELECTED`/`CONFIRMED`/`IN_PROGRESS`→pactive,
`DONE`→done, `CLOSED`→closed (со звёздами), остальные терминальные→closed
(без звёзд). `pconfirm` — локальное состояние внутри `/planned/[id]`, не
маршрут (как в мобильной спеке).

## Визард `/planned/new` — 3 шага, узкая колонка

Единый widget с общим степпером/заголовком сверху (тот же паттерн общего
хедера над шагами, что и в визарде Фазы B), но **без второй колонки** —
контент шага в `max-w-[560px]`, по центру:

- **Шаг 1** (pw1): категория + описание + фото (переиспользует `apiUpload`
  из Фазы B без изменений) + адрес текстом + район + подъезд/этаж/квартира
  + комментарий. Сохранённые адреса (`GET /addresses`) — тот же чиповый
  выбор, что в визарде Фазы B.
- **Шаг 2** (pw2): 5 чипов ближайших дат (в пределах `PLANNED_HORIZON_DAYS`)
  + 4 чипа временных слотов, комбинируются на фронте в `slotStart`/`slotEnd`
  ISO-строки + необязательное поле бюджета.
- **Шаг 3** (pw3): текстовая сводка «как увидят мастера» (без карты — по
  определению нет геоданных для превью) + кнопка «Опубликовать» →
  `POST /planned-orders`.

Побочно чинится тот же баг, что и в мобильной Фазе C: старый
`PlannedNewOrderPage.tsx` отправляет несуществующий `scheduledAt` —
новый визард с самого начала использует `slotStart`/`slotEnd`.

## `/planned/[id]` — статус-driven шелл

Тонкий шелл (тот же паттерн, что `OrderPage` Фазы B — `useParams`,
`GET /planned-orders/:id`, подписка на `order:status`/аналогичное
плановое realtime-событие, ре-загрузка при смене статуса), рендерит
один из видов по статусу. Все виды — узкая колонка, без карты:

- **pwait** (`PUBLISHED`): вертикальный список карточек ставок (не
  grid — решение пользователя: минимальная адаптация, тот же вид, что и
  в остальных экранах фазы). Каждая карточка — рейтинг/опыт/
  `completedCount`/verified (уже приходят с бэка через `enrichBids`),
  бейдж «Лучшая цена» у минимальной ставки (та же логика одного правила
  ранжирования, что в мобильной спеке — не изобретаем новую метрику).
  Кнопка «Выбрать» → локальное состояние `pconfirm`. Кнопка
  «Сравнить (N)» → `/planned/[id]/compare`. Кнопка «Отменить» →
  `POST /planned-orders/:id/cancel`.
- **pconfirm** (локальное состояние, не отдельный вид/маршрут): сводка
  выбранной ставки + предупреждение про `PLANNED_CONFIRM_TIMEOUT_S`
  (2 часа) + кнопка «Подтвердить» → `POST /planned-orders/:id/select`
  `{bidId}`. «Назад» сбрасывает состояние.
- **pactive** (`MASTER_SELECTED`/`CONFIRMED`/`IN_PROGRESS`): два
  подсостояния одного компонента — «Ждём подтверждения» (реальный
  обратный отсчёт от `confirmDeadline`, тот же паттерн живого таймера,
  что `priceDeadline` в Фазе B) и «Подтверждено» (карточка мастера,
  `tel:`-кнопка звонка, сводка цены/времени). Кнопка «Отменить» видна до
  `DONE` включительно.
- **`PlannedDoneView`/`PlannedClosedView`**: отдельные от Фазы B
  компоненты (не импорт `DoneView`/`ClosedView` — другая форма цены,
  только `workPrice`, без разбивки `calloutPrice`/`serviceFee`). Рейтинг
  на closed — `POST /planned-orders/:id/review`, `review` уже приходит в
  деталях заявки.

## `/planned/[id]/compare` — таблица на всю ширину

Единственный экран фазы без `max-w-[560px]` — по решению пользователя
таблица растягивается на всю доступную ширину контентной области
(`w-full`, без искусственного потолка), горизонтальный скролл-контейнер
как страховка на случай реально тесного окна, а не как основной паттерн
(в отличие от мобильной версии, где скролл включался уже при 3 ставках).
Колонки — по одной на ставку (до `PLANNED_MAX_BIDS`=5), строки:
аватар-инициалы+имя, цена, рейтинг, `completedCount`, опыт, срок,
комментарий. Кнопка «Выбрать {имя}» под каждой колонкой вызывает тот же
колбэк перехода в `pconfirm`, что и карточка в pwait (общий обработчик,
поднятый в `/planned/[id]`, не дублируется).

## Спор

`app/(app)/planned/[id]/dispute/page.tsx` — тонкая обёртка, один в один
с `app/(app)/order/[id]/dispute/page.tsx`, меняется только `kind`. Ни
`DisputeView`, ни бэкенд не трогаются.

## Данные, сокеты, ошибки

- **Данные**: `GET /planned-orders/:id`, `POST /planned-orders`,
  `POST /planned-orders/:id/{select, cancel, confirm-completion, review}`,
  `GET /addresses`, `POST /uploads` — все уже реализованы в `apps/api`.
- **Realtime**: подписка на изменение статуса заявки в шелле `/planned/[id]`
  (тот же `getSocket()` из `apps/client/lib/socket.ts`, событие для
  плановых заявок по аналогии с `order:status`).
- **Ошибки**: тот же инлайн `text-danger` + retry паттерн, что в Фазах A/B.

## Тестирование

Без фронтенд юнит-тестов (та же практика, что в Фазах A/B) —
верификация каждой задачи через `pnpm --filter client build`. Финальная
задача фазы — живая браузерная проверка всех статусов планового цикла:
визард (3 шага, включая фото) → pwait с несколькими ставками → compare →
pconfirm→select → pactive (ожидание→подтверждено, реальный таймер) →
done (подтверждение выполнения) → closed (оценка звёздами, проверено в
БД) → отдельно: спор на плановой заявке.

## Вне скоупа

- История заказов, профиль, адреса (CRUD), поддержка, платежи — Фаза D.
- Редизайн ролей мастера/оператора — подпроекты 3 и 4.
- Лид-кредиты — не видны клиенту вообще (сторона мастера).
- Grid-раскладка pwait — рассмотрена и отклонена пользователем в пользу
  минимальной адаптации (единая узкая колонка).

## Самопроверка

Все маршруты/виды покрыты, оба десктоп-специфичных решения (раскладка
pwait/визарда, ширина compare) явно приняты пользователем, а не оставлены
как TBD. Контракты не пересматриваются — те же, что уже провалидированы
мобильной Фазой C цикла «клиент v2» и Cycle 1 бэкенда.
