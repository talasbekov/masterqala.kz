# Дизайн: публичный сайт MasterQala.kz (Next.js) — подпроект 1 из 4

Дата: 2026-07-28
Статус: утверждено пользователем в брейнсторминге, готово к плану реализации.

## Контекст

Текущий `apps/web` (React 19 + Vite + Tailwind 4, `packages/ui`) — единственный
фронтенд проекта, обслуживает клиента, мастера и оператора в одном мобильном
PWA. Дизайн и UX сделаны mobile-first (карточка по центру узкого экрана) и не
подходят для десктопа. Публичных, не требующих входа страниц нет вовсе — сайт
целиком за экраном входа по SMS-коду.

Задача — переписать фронтенд под нормальный десктопный интерфейс. Это
решение слишком большое для одной спеки (три актора: клиент/мастер/оператор
+ новый публичный слой), поэтому разбито на 4 независимых подпроекта:

1. **Каркас + публичные SEO-страницы** (эта спека)
2. Клиентский флоу (заказ услуг, кошелёк, адреса) — desktop-редизайн, новый стек
3. Флоу мастера (работа с заявками, lead-кредиты, анкета)
4. Оператор/админка (верификация, споры, выплаты, security-дашборд)

Мобильное приложение — отдельный, полностью независимый трек, стартует
после того, как веб-часть (все 4 подпроекта) будет закончена. Вне скоупа
этой и последующих трёх спек.

## Продукт и платформа

Маркетплейс бытовых услуг «на дом» (Казахстан): сантехника, электрика,
бытовая техника, замки и двери, мелкий ремонт, другие услуги. Два режима
заявки — срочный и плановый (см. `docs/product/spec.md`).

Эта спека — только публичный, не аутентифицированный слой: лендинг,
страницы категорий, страница для мастеров, справочные страницы. Ни одного
экрана с бизнес-логикой (заказ, оплата, статусы) здесь нет.

## Архитектура и границы

- Новый workspace-пакет **`apps/site`** — Next.js 15 (App Router), рядом с
  `apps/api`, `apps/web`, `packages/ui` в существующем pnpm-монорепо.
- **Домены** (когда появится реальный домен — сейчас staging живёт на
  ngrok, см. `docs/technical/DEPLOYMENT_RUNBOOK.md`):
  `masterqala.kz` → `apps/site`, `app.masterqala.kz` → старый `apps/web`
  без изменений. Реализация через отдельные origin на reverse proxy —
  без path-проксирования между двумя разными фреймворками.
- `apps/web` **не удаляется и не меняется** в рамках этого подпроекта —
  живёт параллельно до завершения подпроекта 4, затем полностью выводится
  из эксплуатации. Это осознанное временное дублирование, а не постоянная
  архитектура.
- `apps/site` не содержит ни одного экрана авторизации. Все CTA — обычные
  `<a href>` на `app.masterqala.kz/...`.
- **Данные**: единственный динамический источник — список категорий
  (`GET /categories` или эквивалент, сверить при реализации, каких точных
  полей отдаёт эндпоинт). Забирается на этапе сборки/ISR (`revalidate` раз
  в 24ч), не клиентским запросом при каждом заходе. Всё остальное
  (тексты хиро, FAQ, «как это работает») — статичный контент в коде
  страниц, без CMS.
- **Дизайн-система**: переиспользуются только CSS-токены брендинга из
  `packages/ui/src/tokens.css` (уже экспортируется пакетом через
  `"./tokens.css"` в `package.json`) — цвета (`--color-primary: #166088`,
  фон `--color-background: #F2F7FA`, шрифт `Manrope` и т.д.), радиусы,
  тени. Сами React-компоненты `packages/ui` (мобильные карточки) не
  переиспользуются — desktop-компоненты (хиро, сетка категорий, футер)
  пишутся заново внутри `apps/site`.

## Данные, ошибки, проверка

**Ошибки**:
- Неизвестный `slug` в `/categories/[slug]` → `notFound()` → страница 404.
- API недоступен на ревалидации ISR → Next отдаёт последний закэшированный
  контент (стандартное поведение), страница не падает и не показывает
  ошибку пользователю.
- Внешние ссылки на `app.masterqala.kz` — обычный `<a href>`, без рантайм-
  проверки доступности целевого приложения.

**Тестирование**: статический контент без бизнес-логики — юнит-тестов не
пишем. Проверка вручную через дев-сервер и продакшн-сборку
(`next build && next start`): все 5 маршрутов рендерятся, категории
подтягиваются с реального API, ссылки на `app.masterqala.kz` корректны,
несуществующий slug отдаёт 404.

## Вне скоупа

- Клиентский, мастерский, операторский флоу — подпроекты 2-4.
- Мобильное приложение — отдельный трек после завершения всех 4 веб-
  подпроектов.
- CMS/редактирование контента без деплоя — не нужно для 5 статичных
  страниц.
- Прод-деплой `apps/site` (Dockerfile, reverse proxy на реальном домене) —
  отдельная механическая задача, не часть дизайна страниц.
