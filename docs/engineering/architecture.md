# Архитектура

## Стек

| Слой | Технология | Почему так |
|---|---|---|
| API | NestJS 10 + TypeScript | Модульность из коробки, DI для подмены интеграций моками |
| ORM | Prisma | Типобезопасные запросы; гео-поля идут мимо неё сырым SQL |
| БД | PostgreSQL 16 + PostGIS | Гео-подбор мастеров и очередь живут в той же БД, что и данные |
| Очередь | pg-boss | Отложенные джобы транзакционно рядом с данными; ноль новой инфраструктуры |
| Realtime | Socket.IO | Офферы мастеру и статусы клиенту без перезагрузки |
| Веб | React 19 + Vite + React Router 7, PWA | Одно приложение на клиента, мастера и оператора — без установки из сторов |
| UI-кит | `packages/ui` | Собственные токены и компоненты, общие для всех ролей |
| Монорепо | pnpm workspaces | — |

Единственный внешний рантайм-сервис — PostgreSQL. Ни Redis, ни S3, ни брокера
сообщений: всё состояние в одной базе. Это сознательный выбор на текущем масштабе,
границы его применимости — в [STATUS.md](../STATUS.md#предел-текущей-архитектуры).

## Сквозной поток: срочная заявка

```
Клиент                      API                          Мастер
  │                          │                             │
  ├─ POST /orders/preview ──▶ pricing: считает выезд        │
  │◀── «Выезд: N ₸» ─────────┤                             │
  │                          │                             │
  ├─ POST /orders ──────────▶ payments.hold(calloutPrice)   │
  │                          │ статус → SEARCHING           │
  │                          │ queue.send('order-wave')     │
  │                          │                             │
  │                          ├─ волна 1: ST_DWithin 3 км ──▶│ WS offer:new
  │                          │   таймаут 60 с              │
  │                          ├─ волна 2: 6 км, 60 с ──────▶│
  │                          ├─ волна 3: 10 км, 90 с ─────▶│
  │                          │                             │
  │                          │◀─ POST /orders/:id/accept ──┤
  │                          │ атомарный гейт: первый берёт │
  │◀── WS order:status ──────┤ остальным WS offer:closed ──▶│
  │   (виден телефон)        │ payments.capture             │
  │                          │                             │
  │◀── WS master:location ───┤◀─ WS geo:update ────────────┤ «Еду»
  │                          │◀─ POST /orders/:id/on-site ─┤ «На месте»
  │◀── цена работ ───────────┤◀─ POST .../propose-price ───┤
  ├─ POST .../confirm-price ▶ 15 мин, иначе авто-отмена     │
  │                          │◀─ POST /orders/:id/complete ┤ «Выполнено»
  ├─ POST .../confirm-completion ▶ 24 ч, иначе авто-закрытие│
  │                          │ wallet: +(выезд − сбор) ────▶│
```

Оплата работ проходит **мимо платформы** — напрямую клиент мастеру. Платформа
касается только стоимости выезда.

## Как решаются гонки

Это самая нагруженная часть системы: три мастера могут нажать «Принять» одновременно,
а pg-boss имеет право доставить джобу дважды.

**Переходы статусов — атомарный гейт.** Каждый переход идёт через `updateMany` с
проверкой текущего статуса в `WHERE`. Если строк обновилось ноль — статус уже изменил
кто-то другой, и сервис отвечает `409`, а не перезаписывает состояние. Метод `gate()`
в [`orders.service.ts`](../../apps/api/src/orders/orders.service.ts).

**Волны защищены монотонным гейтом.** Джоба волны обновляет заявку с условием
`wave: { lt: wave }`. Повторная доставка той же джобы не пройдёт условие и не разошлёт
офферы второй раз.

**Лимит SMS — advisory-lock.** Иначе два параллельных запроса кода прочитали бы один
и тот же счётчик и оба прошли лимит.

**Начисления и ставки — уникальные индексы.** `Accrual.orderId`, `OrderOffer`
`(orderId, masterUserId, attempt)`, `PlannedOrderBid` `(plannedOrderId, masterUserId)`.
Идемпотентность обеспечивается базой, а не аккуратностью кода.

**Списание кредита — условный декремент.** `updateMany` с `balance: { gte: 1 }`:
параллельные отклики не уведут баланс в минус.

## Фоновые джобы

Имена — в [`queue.constants.ts`](../../apps/api/src/queue/queue.constants.ts).

| Джоба | Тип | Что делает |
|---|---|---|
| `order-wave` | отложенная | Разослать офферы мастерам текущей волны |
| `order-wave-timeout` | отложенная | Волна молчит → следующая волна или `NO_MASTERS` |
| `order-price-timeout` | отложенная | 15 мин без подтверждения цены → `CANCELLED_BY_CLIENT` с компенсацией мастеру |
| `order-auto-close` | отложенная | 24 ч после `DONE` → `CLOSED`; замораживается при открытом споре |
| `planned-order-expiry` | отложенная | Слот прошёл без ставок → `EXPIRED` |
| `planned-order-confirm-timeout` | отложенная | 2 ч без подтверждения → назад в `PUBLISHED`, кредит возвращается |
| `planned-order-auto-close` | отложенная | 24 ч после `DONE` → `CLOSED` |
| `presence-sweep` | cron `* * * * *` | Мастера без сигнала > 5 мин → офлайн |

Все таймауты — это `startAfter` у pg-boss, а не таймеры в процессе: рестарт API их
не теряет. При `PGBOSS_DISABLED=1` (e2e-тесты) `queue.send()` становится no-op —
поэтому таймауты в тестах проверяются вызовом обработчика напрямую.

## Realtime

Socket.IO, JWT проверяется в handshake — невалидный токен получает `connect_error`
и до обработчиков не доходит. Каждое соединение вступает в комнату `user:{id}`;
адресная доставка идёт в неё.

**Сервер → клиент**

| Событие | Кому | Когда |
|---|---|---|
| `offer:new` | мастеру | Заявка попала в его волну |
| `offer:closed` | мастеру | Забрал другой / истёк таймаут / отменена |
| `order:status` | обеим сторонам | Любая смена статуса срочной заявки |
| `planned:status` | обеим сторонам | Смена статуса плановой заявки |
| `bid:*` | клиенту | Появилась или изменилась ставка |
| `master:location` | клиенту | Позиция и ETA мастера, пока он в пути |

**Клиент → сервер**

| Событие | От кого |
|---|---|
| `presence:online { lat, lng }` | мастер включил тумблер |
| `presence:offline` | мастер выключил тумблер |
| `geo:update { lat, lng }` | мастер шлёт позицию; ретранслируется клиенту активной заявки |

Разрыв соединения переводит мастера в офлайн немедленно; `presence-sweep` — страховка
на случай, если `disconnect` не долетел.

## Веб-приложение

`apps/web` — одна PWA на все три роли. Ветвление по роли — не по сборке, а по данным:
вкладка «Работа» видна только пользователю с активным `MasterProfile`, раздел `/admin` —
только `role === 'OPERATOR'`.

Два layout-а: `AppShell` — экраны с таб-баром (главная, каталог, заявки, профиль);
`Layout` — полноэкранные сценарии (создание заявки, карточка заявки, кошелёк, спор).

Состояние сервера — React Query; WebSocket-события инвалидируют соответствующие
запросы, поэтому экран обновляется без ручного рефетча. Точка входа сокета —
[`apps/web/src/socket.ts`](../../apps/web/src/socket.ts).

## Хранение файлов

Документы мастера, фото заявок и доказательства споров лежат на локальном диске
(`UPLOAD_DIR`), в БД — только путь и метаданные. Отдаются не статикой, а через
контроллеры с проверкой прав: фото заявки увидит только её клиент, назначенный мастер
или оператор. При переезде на несколько инстансов API это первое, что придётся
заменить на объектное хранилище.
