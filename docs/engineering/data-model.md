# Модель данных

Источник истины — [`apps/api/prisma/schema.prisma`](../../apps/api/prisma/schema.prisma).
Этот документ объясняет, **зачем** нужна каждая сущность и какие инварианты она держит;
точные типы полей смотрите в схеме.

СУБД — PostgreSQL 16 с расширением PostGIS. Все денежные суммы — целые числа в тенге
(`Int`), дробных копеек нет.

---

## Пользователи и роли

**Роль в системе только одна — `UserRole { CLIENT, OPERATOR }`.** Роли `MASTER` не
существует: мастер — это `User` (по умолчанию `CLIENT`), у которого есть связанный
`MasterProfile` со статусом `ACTIVE`. Это регулярный источник путаницы при чтении спеки,
где «Мастер» описан как отдельный актор.

| Модель | Назначение | Ключевые инварианты |
|---|---|---|
| `User` | Аккаунт. Заводится по номеру телефона при первом входе | `phone` уникален. `isBlocked` перекрывает вход и API целиком |
| `MasterProfile` | Анкета мастера: ФИО, ИИН, район, опыт, статус верификации | `userId` уникален — один профиль на пользователя |
| `MasterCategory` | Категории, в которых мастер работает | Составной PK `(masterProfileId, categoryId)` |
| `MasterDocument` | Загруженные удостоверение и подтверждение квалификации | Файл на диске, в БД — путь и метаданные |
| `VerificationDecision` | Журнал решений оператора по анкете | Не перезаписывается — история всех решений |
| `MasterPresence` | Онлайн-статус и последняя геопозиция мастера | `location` — `geography(Point, 4326)`; поддерживается WebSocket-ом и cron-джобой |
| `Category` | Справочник категорий услуг | `slug` уникален; сиды — см. [`prisma/seed.ts`](../../apps/api/prisma/seed.ts) |
| `Address` | Сохранённые адреса клиента | `isDefault` — не более одного на пользователя (обеспечивается сервисом) |
| `SmsCode` | Одноразовые коды входа | TTL 5 мин, счётчик `attempts` до 5 |
| `AuditLog` | Действия оператора и системы над чужими объектами | Только append; `actorType` различает `OPERATOR` и `SYSTEM` |

### Статусы мастера

`MasterStatus { PENDING_REVIEW, NEEDS_INFO, ACTIVE, REJECTED }`

Только `ACTIVE` допускает работу. Кроме статуса, мастера от заявок отсекают два
временны́х поля `MasterProfile`:

- `blockedUntil` — временная блокировка за отмены (7 дней после третьей за 30 дней);
- `priorityPenaltyUntil` — понижение приоритета на 24 ч.

## Срочные заявки

| Модель | Назначение |
|---|---|
| `Order` | Срочная заявка. Держит и цену выезда, и цену работ, и весь таймлайн |
| `OrderOffer` | Факт отправки оффера конкретному мастеру в конкретной волне |
| `OrderPhoto` | Фотографии проблемы, приложенные клиентом |
| `PaymentTransaction` | HOLD / CAPTURE / VOID по заявке |
| `Accrual` | Начисление компенсации выезда мастеру |

**Деньги на заявке.** `calloutPrice` — полная стоимость выезда, которую платит клиент.
`serviceFee` — доля платформы внутри неё. Мастеру начисляется разность
`calloutPrice − serviceFee`. Холдится и списывается **полная** `calloutPrice` — иначе
платформе нечем платить компенсацию (обоснование — комментарием прямо в
[`orders.service.ts:109`](../../apps/api/src/orders/orders.service.ts:109)).

**Защита от двойного начисления:** `Accrual.orderId` — `@unique`. Повторный вызов
начисления упрётся в констрейнт, а не создаст второе начисление.

**Защита от дублей офферов:** `OrderOffer` уникален по `(orderId, masterUserId, attempt)`.
`attempt` растёт при повторном поиске, поэтому один и тот же мастер может получить
оффер по той же заявке снова — но только в новой попытке.

### Статусы заявок

`OrderStatus` — 13 значений. Слева — как это называется в
[спеке](../product/spec.md#5-состояния-заявки-state-machine), справа — как в коде.
**В документации и коммитах пишите правый столбец.**

| В спеке | В коде | Смысл |
|---|---|---|
| `СОЗДАНА` | `CREATED` | Создана, поиск ещё не запущен |
| `ПОИСК_МАСТЕРА` | `SEARCHING` | Идут волны рассылки |
| `ПРИНЯТА` | `ACCEPTED` | Мастер забрал заявку; контакты раскрыты |
| `МАСТЕР_В_ПУТИ` | `MASTER_ON_WAY` | Мастер нажал «Еду»; клиенту видна его позиция и ETA |
| `ОСМОТР` | `INSPECTION` | Мастер на месте, оценивает объём |
| `ОЖИДАНИЕ_ПОДТВЕРЖДЕНИЯ_ЦЕНЫ` | `AWAITING_PRICE_CONFIRM` | Цена работ названа, у клиента 15 мин |
| `В_РАБОТЕ` | `IN_PROGRESS` | Цена принята, работа идёт |
| `ВЫПОЛНЕНА` | `DONE` | Мастер отметил выполнение, ждём клиента |
| `ЗАКРЫТА` | `CLOSED` | Терминальный успех |
| `НЕТ_МАСТЕРОВ` | `NO_MASTERS` | Все волны пусты; холд снят |
| `ОТМЕНЕНА_КЛИЕНТОМ` | `CANCELLED_BY_CLIENT` | Терминальная отмена клиентом |
| `ОТМЕНЕНА_МАСТЕРОМ` | `CANCELLED_BY_MASTER` | Промежуточная: поиск возобновляется |
| `СПОР` | `DISPUTE` | Разбирается оператором |

Наборы «активных» статусов для выборок вынесены в
[`order.constants.ts`](../../apps/api/src/orders/order.constants.ts) —
`ACTIVE_CLIENT_STATUSES` и `ACTIVE_MASTER_STATUSES`. Не перечисляйте статусы руками
в новых запросах, используйте их.

`OfferOutcome { PENDING, ACCEPTED, LOST, EXPIRED }` — исход оффера. `LOST` означает
«успел другой мастер», `EXPIRED` — истёк таймаут волны.

## Плановые заявки

| Модель | Назначение |
|---|---|
| `PlannedOrder` | Плановая заявка со слотом `slotStart`/`slotEnd` |
| `PlannedOrderBid` | Ставка мастера: цена, срок, комментарий |
| `PlannedOrderPhoto` | Фотографии от клиента |

**Ставка уникальна по `(plannedOrderId, masterUserId)`** — один мастер, одна ставка.
Лимит на заявку — 5 ставок, константа `PLANNED_MAX_BIDS`.

`selectedBidId` — `@unique` со стороны `PlannedOrder`: выбранная ставка не может
принадлежать двум заявкам.

### Статусы плановых заявок

`PlannedOrderStatus` — 11 значений.

| В спеке | В коде |
|---|---|
| `СОЗДАНА` | `CREATED` |
| `ОПУБЛИКОВАНА` | `PUBLISHED` |
| `МАСТЕР_ВЫБРАН` | `MASTER_SELECTED` |
| `ПОДТВЕРЖДЕНА` | `CONFIRMED` |
| `В_РАБОТЕ` | `IN_PROGRESS` |
| `ВЫПОЛНЕНА` | `DONE` |
| `ЗАКРЫТА` | `CLOSED` |
| `ИСТЕКЛА` | `EXPIRED` |
| `ОТМЕНЕНА` (клиентом) | `CANCELLED_BY_CLIENT` |
| — | `CANCELLED_BY_MASTER` |
| `СПОР` | `DISPUTE` |

Отличие от срочного режима: `MASTER_SELECTED` при таймауте подтверждения возвращается
в `PUBLISHED` (а не в терминальный статус), и кредит выбранному мастеру возвращается.

## Деньги мастера

Два **раздельных** баланса. Путать их нельзя: один выводится, другой нет.

| Модель | Что это | Выводится? |
|---|---|---|
| `MasterWalletAccount` | Денежный баланс в тенге — компенсации выезда | Да, от 5 000 ₸ |
| `LeadCreditAccount` | Баланс lead-кредитов — валюта откликов на плановые | Нет, только тратится |

| Модель | Назначение |
|---|---|
| `LeadCreditTransaction` | История движения кредитов: `PURCHASE`, `SPEND`, `REFUND`, `PENALTY` |
| `LeadCreditPurchase` | Покупка пакета кредитов |
| `WithdrawalRequest` | Заявка на вывод: `PENDING` → `PAID` / `FAILED` |
| `MasterCancellation` | Отмены мастером за последние 30 дней — вход для блокировки |

Баланс кредитов **может уйти в минус**: штраф `−2` списывается независимо от остатка
(см. [`master-penalty.service.ts`](../../apps/api/src/common/master-penalty.service.ts)).
Это осознанно — иначе штраф можно обойти, обнулив баланс.

## Споры и отзывы

`Dispute` привязывается **либо** к `orderId`, **либо** к `plannedOrderId` — оба поля
опциональны, заполнен ровно один. Так же устроен `Review`, где обе связи ещё и `@unique`:
один отзыв на заявку.

Решение оператора раскладывается на три поля: `refundServiceFee` (вернуть сбор),
`penalizeMaster` (санкция мастеру) и `resolutionNote` (обоснование текстом).
Возврат сервисного сбора применим только к срочным заявкам — в плановых платформа
денег клиента не держит.

## Геоданные

Два поля типа `geography(Point, 4326)`, обозначенные в Prisma как `Unsupported`:
`Order.location` и `MasterPresence.location`. Prisma Client их не читает и не пишет —
все операции с ними идут **сырым SQL** через `$queryRaw`. Основные потребители:

- подбор кандидатов волны — `ST_DWithin` в [`matching.service.ts`](../../apps/api/src/orders/matching.service.ts);
- расстояние и ETA — `ST_Distance` в [`postgis-routing.service.ts`](../../apps/api/src/routing/postgis-routing.service.ts).

Если добавляете поле рядом с `Unsupported`, проверяйте, что `prisma db pull` не внёс
в схему служебную таблицу `spatial_ref_sys` — её присутствие ломает миграции
(уже ловили в коммите `0c553ee`).

## Риски хранения персональных данных

Приняты осознанно на текущем этапе, но должны быть закрыты до боевых пользователей.
Развёрнутый разбор — в [technical/DATA_MODEL.md](../technical/DATA_MODEL.md).

| Что | Риск |
|---|---|
| `MasterProfile.iin` | ИИН хранится строкой **без шифрования и токенизации**. Это персональные данные повышенной чувствительности |
| `MasterDocument` | Удостоверения и подтверждения квалификации лежат файлами на диске, отдаются через контроллер с проверкой прав — но сами не зашифрованы |
| `SmsCode.code` | Код хранится открытым текстом. Записи не подчищаются: retention и cleanup-джобы нет |
| Сессии | Модели устройств/сессий нет — отозвать выданный JWT невозможно (см. [STATUS.md](../STATUS.md#прод-блокеры)) |

## Правила изменения модели

1. Любое изменение `schema.prisma` сопровождается миграцией — правка схемы без
   миграции ломает деплой, где применяется `prisma migrate deploy`.
2. На проде накатывается **только** `prisma migrate deploy`. `migrate dev` — локально:
   он умеет пересоздавать базу.
3. Поля рядом с `Unsupported` требуют проверки, что `prisma db pull` не затянул
   `spatial_ref_sys` (см. выше).
4. Изменение статуса, таймаута или финансового поведения считается незавершённым,
   пока не обновлены код, тесты и документ в том же workstream.
