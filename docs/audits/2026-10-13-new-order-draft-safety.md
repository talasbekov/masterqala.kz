# Current-order draft safety

## Scope and decisions

Additive safety work on the existing four-step current-order form. The API payload, categories, address contract, direct/legacy commercial-mode selection and server fees are unchanged. This does not implement the separate planned-order flow or redesign the new-order screen (Figma mobile source 118:1427).

One versioned editable-draft record in the current tab's sessionStorage (`mq.new-order.draft.v1`) contains its authenticated owner ID and editable step/category/description/address/coordinates plus at most five submitted uploaded-photo references. It does not contain credentials, files, blob/data previews, prices, availability, approval or pending requests. Another account cannot restore the record; an owner mismatch removes this one bounded record rather than retaining per-owner caches. A closed tab normally discards sessionStorage. Storage-denied environments remain usable without persistence.

Explicit logout discards this tab's draft and invalidates mounted writers, while retaining canonical language preferences and unrelated storage. Ordinary navigation, form Back, locale rerenders, reload/remount and request failures retain the draft. A separate single owner-scoped pending-create marker contains only an exact local request ID. It is persisted before POST; the editable session is frozen, and same-owner remount blocks resubmission. A matching confirmed response can resolve that marker even after the original form unmounts. Old responses cannot erase another owner or a newer request. Explicit logout discards both records. Unknown outcomes offer Next Link owned-orders/support links that retain the current document and no blind reset/retry. Owner-keyed form mounting prevents another account's values from appearing during transition.

Initial geolocation is independent of translations. Explicit My location requests use a selection revision so a later saved address/map selection or newer location request wins over an older callback. It cannot overwrite a restored draft or explicit address/map choice. Initialization and preview callbacks are cancelled on effect cleanup. Restored step four requests a fresh server preview; previous prices/availability are never stored. Uploaded references remain subject to the existing server ownership/cleanliness checks at order creation. There is no offline submission queue, heuristic order matching or automatic replay. Full reload destroys a pending promise, so unknown status can remain blocked until server-backed recovery is added. A storage-denied browser has a bounded browser-window owner/request guard that survives same-document route remounts but not a full reload, with an explicit warning that status cannot survive reload. This is conservative containment, not a complete reload-safe duplicate-prevention guarantee; see the separate server idempotency proposal.
